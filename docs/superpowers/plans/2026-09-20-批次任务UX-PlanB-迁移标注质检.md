# Plan B · 迁移 tag / tagcheck 到任务三件套 — 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **Spec:** `docs/superpowers/specs/2026-09-20-批次任务UX设计.md` — **先读它**。
> **前置:** Plan A 已完成并验收(settingsApi / useTaskProgress / TaskLogDrawer / POLL_* 常量已存在)。

**Goal:** `tag`(AI 标注)与 `tagcheck`(手动质检)接入三件套:后端批次大小从 settings 读、前端轮询间隔从 settings 读、日志抽屉换通用壳(带下载)。**行为不变,只有配置来源变。**

**Architecture:** 后端两处批次常量改 `readPoll(db, taskType).batch`(`TAG_BATCH_CAP=16` → settings 的 `poll.tag.batch`,默认 16,语义=批上限;见「批次语义」框);前端 TagPanel 两个 `setTimeout(tick, 500)` 递归轮询改为可配置间隔;TagLogDrawer 内部换 TaskLogDrawer 壳。

> **⚠️ 批次语义辨析(执行者必读,这里是本 plan 唯一的判断题):**
>
> - `tag` 的批次大小现在**不是常量**:是按模型上下文窗动态算的(`tagger.ts:239` `Math.max(1, Math.min(TAG_BATCH_CAP, (ctx-1500)/250))`),`TAG_BATCH_CAP=16` 只是**上限**。
> - `tagcheck` 的 `TAGCHECK_BATCH=200` 是**定长**。
> - 若把 `poll.tag.batch`(假如默认 30)直接当 tag 的批大小,会**放大**现有批次(动态算出 16 上限、30 更大),模型上下文可能爆 —— 所以 tag 的 settings 值语义是**批上限**(替代 TAG_BATCH_CAP 的位置),动态公式保留:`size = clamp(settings.batch, 1, (ctx-1500)/250 往下取整)`,即用户设的值是"最多一批多少条",实际大小仍随上下文收缩。tagcheck 的 settings 值是**定长批大小**。
> - **默认值已在 Plan A 落地为 16/200**(spec §3 与 Plan A DEFAULTS 均已同步,无需再改;本条仅确认)——tag 的语义是**批上限**(替代 TAG_BATCH_CAP=16 的位置),tagcheck 是**定长**(原 TAGCHECK_BATCH=200)。已存库的值不动。

### Task 2: 前端轮询接入(间隔可配)

**Files:**
- Modify: `web/src/components/TagPanel.tsx`(两处轮询循环)

**Interfaces:**
- Consumes: Plan A 的 `useTaskProgress`、`settingsApi`。
- Produces: 无新接口;TagPanel 行为不变、间隔可配。

**改造决策(执行者必读)**:TagPanel 现有轮询是 `setTimeout` 递归(带 stopped 守卫、日志长度判等、错误收尾),**比 useTaskProgress 的哑轮询丰富**。硬换成 hook 会把收尾逻辑拆散。**裁决:不换 hook,只换间隔来源** —— TagPanel 挂载时 `settingsApi.getPolls()` 取 `poll.tag.interval_ms` / `poll.tagcheck.interval_ms`(失败 500 兜底,保持现状节奏),两个递归轮询的 `setTimeout(tick, 500)` 改 `setTimeout(tick, intervalRef.current)`(intervalRef 由配置填充)。useTaskProgress hook 保留给 Plan C 的 proposals(它的轮询是纯哑轮询)——spec §4.1 说「调用方迁移成本=把 setInterval 换成 hook」对本组件不适用,因为它不是哑轮询;这是对 spec 的偏离,记录在 plan 里,spec 不改( hook 对未来新任务仍成立)。

- [ ] **Step 1: 配置拉取**

TagPanel 组件内加:

```tsx
// 任务三件套(spec §2):轮询间隔按任务可配。拉失败兜底 500ms 保持现节奏
const tagIntervalRef = useRef(500);
const checkIntervalRef = useRef(500);
useEffect(() => {
  settingsApi.getPolls()
    .then((polls) => {
      if (polls.tag) tagIntervalRef.current = polls.tag.intervalMs;
      if (polls.tagcheck) checkIntervalRef.current = polls.tagcheck.intervalMs;
    })
    .catch(() => {}); // 拉不到照旧 500ms
}, []);
```

- [ ] **Step 2: 换间隔**

`startPolling` 与 `startCheckPolling` 里 `timer = setTimeout(tick, 500)` → `timer = setTimeout(tick, tagIntervalRef.current)` / `checkIntervalRef.current`。注释里三处 `500ms` 字样同步改成「配置的间隔」。

- [ ] **Step 3: 门禁 + 手动验证**

Run: `cd web && npx tsc --noEmit && npx max build 2>&1 | grep -i "compiled successfully"` → 过。
手动:设置页把标注轮询改 10s → 重进标签页 → 触发标注 → Network 面板 run-progress 间隔 ≈10s(验收核心)。

**Interfaces:**

- [ ] **Step 1: 内部改造**

`TagLogDrawer` 的 Drawer 骨架/贴底/封顶/空态逻辑删掉,换成:

```tsx
import TaskLogDrawer from './TaskLogDrawer';
import type { TagLogLine, TreeChange } from '../types';

/** 对外签名保持不变(spec:TagPanel 零改动) */
export default function TagLogDrawer(props: {
  open: boolean; onClose: () => void; lines: TagLogLine[]; onClear: () => void;
  waiting?: boolean; changes?: TreeChange[];
}) {
  const { lines, changes, ...rest } = props;
  const warnCount = lines.filter((l) => l.type === 'note' && l.level === 'warn').length;
  return (
    <>
      {/* 上一轮变化区块是标签页特有 —— 壳不管它,这里自己渲染在抽屉内容顶部。
          壳不支持顶部额外内容 → 把它包进第一行 renderLine?不行,它是独立区块。
          处理:changes 区块渲染在 TaskLogDrawer 外面不可行(Drawer 是壳的一部分)……
          见 Step 2 的壳扩展。 */}
      <TaskLogDrawer
        {...rest}
        title="标注日志"
        lines={lines}
        warnCount={warnCount}
        downloadName={(d) => `标注日志-${d}.txt`}
        renderLine={(l) => <LogRow line={l} />}
        serialize={(ls) => ls.map((l) => noteText(l)).join('\n')}
      />
    </>
  );
}
```

- [ ] **Step 3: LogRow 与 serialize 保持**
