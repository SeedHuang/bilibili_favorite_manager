# 批次任务 UX 标准 — 设计 spec

> 2026-09-20 brainstorming 定稿。本文自包含:执行者只读本文 + 三个 plan 即可实施,无需对话历史。
> 相近文档:[docs/prds/批次任务UX规则.md](../../prds/批次任务UX规则.md) 是早期 PRD;**以本文为准**(本文修正了 PRD 的两处,见 §0)。

## §0 相对 PRD 的修正

1. **`proposals` 不配 batch 键**:方案生成是一次 LLM 调用,没有批次语义。PRD 写了 `poll.proposals.batch=1`,那是摆设 —— 硬造语义违背 YAGNI。规则补一条:**无批次概念的任务只配 interval_ms 和模型,不配 batch**。
2. **`TaskLogDrawer` 用泛型壳而不是统一 LogLine**:现有 `TagLogLine` 是四种帧的联合类型(phase/item/verdict/note),各有自己的行渲染。压成 `{ts,level,text}` 会丢掉条目名/判词着色等信息。所以通用抽屉只管**布局与行为**(贴底/封顶/清空/下载),行渲染由调用方传 `renderLine` 回调。

## §1 覆盖范围

| taskType | 任务 | 入规约? | 现状缺口 |
|----------|------|--------|---------|
| `tag` | AI 标注(标签页) | ✅ | 轮询间隔硬编码 2s;批次硬编码;日志无下载;抽屉非通用 |
| `tagcheck` | 手动质检(标签页) | ✅ | 同上(3s) |
| `proposals` | 夹子方案生成(规则页) | ✅ | 无中止、无日志抽屉、模型临时借用 `rules`、轮询硬编码 3s |
| `classify` | 整理页 SSE 归类 | ❌ 暂不入 | 整理页后续整页重构时再处理 |
| `chat` / `rules` | 聊天 / 规则建议 | ❌ | 非批次任务(单次调用、无进度),只保留已有模型配置 |

## §2 规则全文(项目级标准,写给未来所有异步任务)

凡是**批次任务(分批处理多单位数据)、AI 调用任务、大数据量处理**:

1. **三件套**:进度条 + 日志抽屉 + 启动/中止控件,缺一不可。
2. **断点在数据,不在任务**:「跑过没」由业务表字段自证(`ai_checked_at` / `checked_at` / 已落地 work_folders)。**不**造任务级 checkpoint 表。
3. **三能力**:能开始、能续、能强制重跑。「开始/继续」合用一个按钮按数据状态换文案;「重新开始」是弹窗里的 scope 选项(`continue`/`all`),不并列三按钮。
4. **日志三能力**:可看(抽屉)、可清(重跑/续跑自动清空重记)、可下载(抽屉按钮导出 .txt)。
5. **任务三件套设置**(设置页按任务一对一):轮询间隔(下拉 1/2/3/5/10s)、批次大小(下拉 1/2/5/10/20/30/40/50 + 自定义 1~500;无批次语义的任务不配此项)、AI 模型(下拉,沿用 LlmPurpose 机制)。
6. **进度契约统一**:progress 接口返回 `{ running, scope?, done, total, error?, logs }`,不自创形状。
7. **日志寿命 = 当前 run**:后端内存数组绑 run;run 结束不清空(留着下载/翻查);下次启动清旧记新。刷新/重启丢历史(已知代价)。
8. **中止 = 显式接口**:abort 后 running→idle,已落库批次保留,未跑丢失。
9. **启动约定**:启动接口返回 202 `{ok:true}`;运行中再启动 409。
10. **批次大小真生效**:后端启动任务时从 settings 读,改设置后下次启动生效(正在跑的不能改)。

## §3 数据与接口

### settings 键(不加表不加列,`getSetting/setSetting` 已有)

```
poll.tag.interval_ms       = '2000'    (默认 2000)
poll.tag.batch             = '16'      (默认 16 —— 语义是**批上限**,替代原 TAG_BATCH_CAP=16 的位置;实际批大小仍随模型上下文窗动态收缩)
poll.tagcheck.interval_ms  = '3000'    (默认 3000)
poll.tagcheck.batch        = '200'     (默认 200 —— 定长批大小,原 TAGCHECK_BATCH=200;保持现网行为)
poll.proposals.interval_ms = '3000'    (默认 3000)
llm.purpose.<taskType>     = entryId   (已有机制,不动)
```

**兜底规则**:settings 缺 key 时用代码内默认值表(上表括号),不预写库。

### 后端接口

```
GET /api/settings/polls              → { polls: Record<string, {intervalMs:number; batch:number|null}> }
PUT /api/settings/polls/:taskType    → body { intervalMs, batch? } → { ok:true }
```

- `batch: null` 表示该任务无批次概念(proposals)
- PUT 校验:intervalMs ∈ {1000,2000,3000,5000,10000};batch ∈ {1,2,5,10,20,30,40,50} 或 1~500 整数(自定义);非法 400
- 未知 taskType 404(白名单:'tag' | 'tagcheck' | 'proposals')

### 前端类型(types.ts 追加)

```ts
export type PollConfig = { intervalMs: number; batch: number | null };
export type PollsMap = Record<string, PollConfig>;
```

(`AsyncTaskProgress` 不强行新建:三个任务现有 progress 形状已接近契约,Plan B/C 迁移时在 hook 的 `toProgress` 里对齐,类型沿用各任务现有定义。)

## §4 前端架构

### 4.1 `useTaskProgress` hook(新建 `web/src/hooks/useTaskProgress.ts`)

```ts
export function useTaskProgress<T>(opts: {
  taskType: string;                        // 查 poll.<taskType>.interval_ms 用
  fetcher: () => Promise<T>;               // 各任务现有 progress 接口
  enabled: boolean;                        // true 才起 interval(运行态)
  onError?: (e: string) => void;
}): T | null;
```

行为:
- 挂载时 `settingsApi.getPolls()` 拿该任务 `intervalMs`(拿不到用 3000 兜底)
- `enabled=true` 时 `setInterval(fetcher, intervalMs)`;`enabled` 或 `intervalMs` 变化时重建 interval
- 每次成功把结果存 state 返回;失败静默(轮询失败下一轮再试,不打断用户)
- 返回最新一次 fetcher 结果;调用方自己从结果里读 running/done/total

**刻意薄**:不吞任务的业务状态(和标注/质检现有轮询一样是「哑轮询」),只把「间隔可配」抽出来。调用方迁移成本 = 把自己的 `setInterval` 换成 hook。

### 4.2 `TaskLogDrawer` 组件(新建 `web/src/components/TaskLogDrawer.tsx`)

泛型壳,复用 `TagLogDrawer` 的全部行为(纯渲染器/贴底跟随/500 行渲染封顶/空态),抽成可配置:

```tsx
export default function TaskLogDrawer<T>({
  open, onClose, onClear, waiting, title,
  lines,                    // T[] — 全量缓冲区,类型由调用方定
  renderLine,               // (line: T, index: number) => ReactNode — 行渲染交给调用方
  serialize,                // (lines: T[]) => string — 下载内容生成;缺省 JSON.stringify(lines, null, 2)
  downloadName,             // 文件名,如 '标注日志-2026-09-20.txt'
}: { ... });
```

- 顶部图标三个:贴底(ArrowDown,沿用)、清空(Eraser,沿用)、**下载(lucide `Download`,新增)** —— onClick 用 `serialize(lines)` 建 Blob 触发 `a[download]`
- 标题显示 `title`(如「标注日志」)+ 行数 + warn 计数(warn 计数逻辑由调用方经 props 传入 `warnCount?: number`,抽屉不再自己数 —— 泛型壳不知道哪行是 warn)
- 现有 `TagLogDrawer` **保留不动**,Plan B 迁移时其内部改用 TaskLogDrawer 壳(见 Plan B)

### 4.3 设置页合一表(`ModelManager.tsx` 重命名为 `TaskSettings.tsx`)

现状:ModelManager 按 purpose 卡片列表,每卡有模型下拉。改造:

- 文件重命名 `web/src/components/ModelManager.tsx` → `TaskSettings.tsx`,导出名同步改,`auth.tsx` 的 import 更新
- 每个 purpose 卡片(即未来的每个任务行)加两列:
  - 轮询间隔 Select:1s/2s/3s/5s/10s,读写 `poll.<taskType>.interval_ms`
  - 批次大小 Select:1/2/5/10/20/30/40/50 + 自定义(弹出 Input 数字 1~500);`batch=null` 的任务(purpose 无对应批次任务,如 chat/rules)不显示此列
  - taskType ↔ purpose 映射:purpose 名即 taskType(`tag`/`tagcheck`/`proposals`);`chat`/`rules`/`classify` 只有模型列
- 改动即保存:Select onChange → `settingsApi.setPoll(taskType, {...})`
- 页面标题区文案从「模型管理」改「任务设置」(模型只是三件套之一)

## §5 错误处理

| 场景 | 行为 |
|------|------|
| `GET /settings/polls` 失败 | hook 用默认 3000ms 兜底继续;设置页显示红条(照页面既有 error 惯例) |
| `PUT` 非法值 | 后端 400 + 中文原因;前端红条显示,不改本地 state |
| 下载空日志 | 照常生成空文件(用户自己判断),不弹错 |
| 后端启动任务时 settings 值非法(手改库) | `readPoll` 兜底默认值并记 warn 日志,不 throw |
| 轮询途中后端重启 | fetcher 失败静默;任务状态接口发现 running=false 自然停轮询 |

## §6 测试策略

- **后端**:vitest 全覆盖(polls repo 三个函数 + 路由校验/兜底/白名单;Plan B/C 的批次读取与 abort 照各文件既有测试模式)。测试命令 `cd server && npx vitest run`,门禁含 `npx tsc --noEmit`
- **前端**:项目**无前端测试基建**(package.json 无 test script),不为本次任务搭 —— 前端门禁 = `npx tsc --noEmit` 0 错 + `npx max build` 输出 "Compiled successfully"(退出码 1 是既有 esbuild 问题,忽略)。hook/抽屉的正确性靠 Plan B/C 迁移后的手动验收清单
- **每个 plan 的验收清单**写在各 plan 末尾,执行完由用户手动过一遍

## §7 Plan 拆分与依赖

```
Plan A(基建) ──→ Plan B(迁移 tag/tagcheck) ──┐
             └──→ Plan C(迁移 proposals) ────┴── 三个任务全部达标
```

- **Plan A**:polls repo + 2 路由 + 前端类型/api + TaskLogDrawer + useTaskProgress + ModelManager→TaskSettings 合一表。不动任何既有任务的运行逻辑。**B、C 都依赖 A 的全部产物**
- **Plan B**:tag/tagcheck 后端读 batch + 前端换 hook + TagLogDrawer 换壳。纯迁移,行为不变(除轮询间隔变成可配)
- **Plan C**:proposals 补中止/日志/独立模型 + 读 interval。改动最深(后端新接口 + 前端新 UI),放最后因为它的「目标形态」最依赖 A 的组件
- B 和 C 相互独立,可并行;都建议在 A 验收通过后开工

## §8 验收标准(全部完成时)

1. 设置页:tag/tagcheck/proposals 三行,每行可配轮询间隔(+批次,+模型);改动立即生效
2. 标注/质检:轮询间隔跟随设置;日志抽屉能下载 .txt;行为与迁移前一致
3. 方案生成:有中止按钮(点了真停);有日志抽屉(能看到裁判丢弃/落库过程);模型独立可配(不再借用 rules);轮询间隔跟随设置
4. `cd server && npx vitest run` 全绿;`npx tsc --noEmit`(server+web)0 错;web build "Compiled successfully"
5. 未来新增异步任务时,按 §2 十条对照执行(这条是规则的长久价值)
