## 9. 分类引擎

### 9.0 整理流程(AI 管家,2026-09-15 用户定稿)

**核心交互原则**:

- **「开始整理」≠ 调 AI**。点「开始整理」是进入**手动编辑状态**(编辑工作台,可手动
  拖拽/合并/改名/移条目),不弹 AI。
- **AI 管家是常驻悬浮图标**,随时可调出,默认动作「整理文件夹」。
- 手动整理 与 AI 整理 是**并行两条路**,AI 是你的助手不是唯一入口。

**AI 管家完整流程**:

```
打开 AI 助手 → 选「整理文件夹」
  ↓
【Step 1 对话达成体系】自由几轮,不限次数
  AI 第一轮:先看你的收藏 + 现有夹子结构,给「我认为最好的收藏方式」建议
             (维度参考:按主题/内容类型,而非按 UP —— 按 UP 太碎)
  你回偏好:想保留哪几个夹子、按什么维度、控制多少个夹子
  AI 调整 → 给你一套建议体系(名字 + 判定规则 + 预估条数)
  你在聊天窗里直接改(改名/合并/拆分/删除)
  轮次自由,直到你说「就这样」或点「重新生成」
  ↓
【Step 2 失效处理】AI 识别已失效条目 → 归入本地「失效文件夹」(真文件夹)
  - 失效文件夹仅本地,sync 时跳过,你在里面统一手动删除
  ↓
【Step 3 归类】AI 把 3000 条归入确认后的体系(每条:归属 + 置信度 + 理由)
  ↓
【Step 4 方案审阅】
  - 左「现在结构」 右「整理后结构」 对比
  - 归类结果可抽查(每条有 ai_reason,点开看为什么归这)
  - 生成「本地整理审计报告」(前后对比,存档)
  - 不满意 → 撤回本地改动(回到整理前)
  ↓
【Step 5 同步到 B站】你手动点(红色醒目 + 二次确认)
  - 慢速写操作(3~5s/次),绝不触发风控
  - 遇 -412 立即停,不重试
  - 实时进度条(具体数字:已移动 x/y · 建夹 a · 剩余约 m 分钟)
  - 生成「同步审计报告」(每请求成败 + 是否触发风控,带 trace_id)
```

**两条审计报告(分开存 `audit_logs` 表)**:

| kind | 内容 | 何时生成 |
|---|---|---|
| `reorganize` | 本地整理前后对比(合并了哪些夹、移动了哪些条目、哪些失效归入本地文件夹) | Step 4 |
| `sync` | 写回 B站:实际发了哪些请求、每个成功/失败、耗时、是否触发风控 | Step 5 |

**撤回边界(诚实声明)**:
- 撤回只对「本地已应用、尚未写回 B站」的部分有效。
- **一旦 Step 5 写了 B站,部分操作不可完全撤回**(尤其删失效)。
- 所以「撤回」在 Step 4 才有完整意义;Step 5 之后给的是「审计报告 + 可撤销清单」。

**AI 对话上下文处理(2026-09-15 红队审查加固 — 不能压缩错东西)**:

**红队发现的问题**:把"用户在聊天窗里直接编辑体系(改名/合并)"当聊天消息压缩 → **等于把已确认的结构化状态压缩成一段话,下次会话要重新解析**。

**修法**:**结构化操作不进入对话历史**,只进独立的结构化存储。

- `session_messages` 只存:用户的指令(短) + AI 的回复(短)+ 提问/答复这类"聊天本质"
- `taxonomy_draft`(M4 新增表)存:用户在聊天窗里直接编辑体系的改动(改名/合并/拆分)
- AI 聊天的"上下文预算" = 最近 N 轮对话原文 + **当前 `taxonomy_draft` 的结构化快照** + 旧轮滚动摘要
- 超限 → 自动把最旧的 1/3 聊天消息压缩成摘要(不影响结构化状态)
- 关键:**压缩聊天消息不会丢失"已确认的体系"**,因为体系状态在 `taxonomy_draft` 里独立保存

**会话列表只显示摘要**(一句话 + 时间),点开才加载全部消息 — 不在聊天窗口期显示完整历史。

### 9.1 Pass 1:提体系

**抽样(2026-09-15 红队加固 — 不让模型在 32K 上下文里塞 400 条)**:

不再是"按夹子大小加权抽 400 条塞给模型"。Pass 1 分两阶段:

```
Step 1 keyword 初分(0 token,纯本地规则):
  - 标题/简介匹配关键词 → 候选夹子(如"Python"→"AI/编程")
  - 未匹配的 → "待 AI 校准"组
  - 这一步已能给"大致分法",token 为 0

Step 2 AI 抽检校准(本地 14b 也跑得动):
  - 从"待 AI 校准"组抽 100 条,**平衡覆盖各关键词簇 + 各夹子**
    (避免一个大夹子吃掉所有配额)
  - 单夹最多抽 15 条(从 400 → 100 → 15/夹,token 降 4 倍)
  - token 消耗:100 条 × 250 ≈ 25K + 系统 prompt ≈ 30K,32K 上下文够
  - AI 输出最终体系(合并 + 重命名 + 拆分)+ 判定规则

**为什么这个改法关键**:
- 400 条在 32K 上下文里塞不下,**Pass 1 一开始就跑不起来**
- 即使塞得下,400 条里大概率有一半是冗余(相似标题集中),AI 看到的"信号"并未增加
- keyword 初分免费且可信,AI 只需在"边界用例"上发力
```

**喂给模型的信号**:
- **用户现有的收藏夹结构和名字** ← 关键。AI 必须先知道现在怎么分的,才能说
  「你原来 42 个夹子该合并成 12 个」
- 用户的约束(如「控制在我 15 个以内」)

**输出**:

```ts
interface TaxonomyProposal {
  folders: {
    tempId: string          // 'f1'
    name: string
    description: string
    rule: string            // Pass 2 要用的判定规则,必须可执行
    estCount: number
    reuseFolderId?: number  // 复用现有夹子,而不是新建
  }[]
  notes: string             // AI 解释它做了什么、为什么
}
```

**`reuseFolderId` 是重点**。B站收藏夹只能改名/删除,不能「改归属」,所以**复用现有夹子
比新建重要得多** —— 否则会堆出几十个语义重复的夹子。Prompt 里明确要求 AI 优先复用。

### 9.1.1 Pass 1 输出校验(2026-09-15 红队加固 — 防 Pass 2 跟着错)

**红队发现的问题**:Pass 1 输出的 `reuseFolderId` 在 Pass 2 里**没有任何校验** → AI 把现有夹子 id 写错(幻觉)→ Pass 2 默默把 3000 条归到一个不存在的夹子。

**修法**:Pass 1 输出后、Pass 2 之前,**硬校验**:

```
1. reuseFolderId 引用不存在的 id → 报错,Pass 2 不启动
2. 同一现有夹子被复用两次 → 报错(去重)
3. 体系里**未复用**的现有夹子 → UI 显式提示「这些夹子 AI 没用,你确认放弃吗?」
   (避免 AI 漏掉了某个夹子里的视频,你误以为它归对了)
4. 同名新建夹子与现有夹子同名 → 警告,让用户在 UI 改
```

任一校验失败 → Pass 2 不启动,UI 展示具体问题(哪个 id 不存在、哪个夹子被重复引用、哪个被忽略)。**这是把"AI 输出幻觉"挡在 Pass 2 之前的关键一步**,不是细节。

### 9.2 UI 编辑提案 ← 「建议权」的落点

改名 / 改规则 / 删除 / **合并两个夹子** / 手动新增 / 加一句约束重新生成。

**重跑 Pass 1 很便宜**(一次 LLM 调用),所以随便试。这就是两阶段设计的价值:
不满意只重跑体系,不用重跑 3000 条归类。

### 9.3 Pass 2:归类

- 输入:确认后的体系(只带 `name` + `rule`)+ **一批 50 条**
- 每条喂给模型的字段(实测确认可用,**不含分区名**):

  | 字段 | 作用 |
  |---|---|
  | `title` | 主信号 |
  | **`intro`** | **主力信号** —— 实测是完整的一段简介,信息量远超标题 |
  | `upper.name` | 作者(同一 UP 的内容常属同类) |
  | `duration` / `pubtime` | 弱信号(短视频 vs 长课程、时效性) |
  | `cnt_info.play` | 弱信号(热度) |

  **不要用 `fav_time` 做分类** —— 那是你什么时候收藏的,和内容主题无关。
  它适合做「最近收藏」筛选,不适合归类的语义判断。
- 输出:`[{ itemId, folderTempId | null, confidence, reason }]`
- `null` = 未归类,落到「待定」,UI 单独一栏让用户手动处理
- 每批独立、可续跑、失败只影响该批
- **一个视频同时属于多个夹子?** B站支持,但让 AI 选**一个主归属**,用户想加第二个手动加

**日常增量路径**:新收藏的条目体系不变,只跑 Pass 2,1~2 次调用搞定。

**批大小**:由当前选中模型的 `contextWindow` 动态算(见 §3 上下文自适应),不硬编码。
本地 14b(32K)≈ 120 条/批,DeepSeek(128K)≈ 500 条/批,1M 上下文可一次全塞。

### 9.4 小模型 JSON 四层兜底

```
1. 要求纯 JSON,不要 markdown 围栏
2. 解析失败 → 剥围栏 / 截取第一个 { 到最后一个 } 重试
3. 再失败 → 缩小批次(50 → 15)重试
4. 再失败 → 该批标记失败,其余批次继续
```
