## 10. 提案(Plan)与执行

### 10.1 Op 类型

```ts
type Op =
  | { kind:'create_folder'; tempId:string; name:string; intro:string; privacy:0|1 }
  | { kind:'rename_folder'; folderId:number; name:string; intro?:string }
  | { kind:'move_item';     itemId:string; to:{tempId:string}|{folderId:number} }
  | { kind:'remove_item';   itemId:string; fromFolderId:number; reason:'invalid' }

interface OpsPlan {
  id: number
  ops: Op[]
  stats:   { createFolders:number; moves:number; removes:number }
  warnings: string[]   // 「12 条未归类」「3 条已在目标夹子里,已跳过」
}
```

**`remove_item` 的语义必须抠清楚**:是「**从这个收藏夹里移除**」,不是「取消收藏」。
UI 文案要写明白,别让人误删。这也是为什么 op 里带 `fromFolderId` 而不是只有 `itemId`。

### 10.1.1 删除保险(2026-09-15 用户拍板,不可违反)

**AI 永不产生删除操作。删除只由用户在 UI 手动发起。**

| 约束 | 说明 |
|---|---|
| AI 产生的 op | **仅限** `create_folder` / `rename_folder` / `move_item` |
| `remove_item`(删条目) | **只允许用户手动录入**,且 `reason` 必须是 `'invalid'`(失效) |
| 删除收藏夹 | **没有对应的 op 类型**,只能用户手动在 UI 点删除 |
| 三道防线 | curator 不生成 → plan 校验拒绝 → execute guards 拦截 |

**「合并夹子」的正确实现**:AI 把 A 的条目全移到 B,**A 空夹子留着,由用户手动删**。
删夹子永远不是 AI 的决定 —— 这是刻意的安全边界。

**对"误删"保持诚实**:
- 删收藏夹 = 释放夹内条目(视频本身还在,只是不再属于该夹),不是删视频。
- 但若该夹是条目唯一归属,删夹 = 该条目从收藏消失。所以删夹必须**手动 + 二次确认**。

### 10.2 生成 ops 时的 diff

- 条目已经在目标夹子里 → **不生成 op**(避免无意义写请求)
- 目标夹子是新建的 → 先 `create_folder`,拿到真 `media_id` 后再被引用

### 10.3 执行顺序(拓扑序,不可乱)

```
1. create_folder   → 拿到真实 media_id
2. rename_folder
3. move_item       → 引用步骤 1 的结果
4. remove_item
```

### 10.4 执行前的本地 dry-run

不花任何 API 请求,校验所有 op:条目还在吗?目标夹子还在吗?引用的 `tempId` 都有定义吗?

### 10.5 可中断 / 可续跑

每个 op 执行前写 `executions` 行(`running`),成功改 `ok`。中断后 plan = `paused`,
续跑从第一个非 `ok` 的 op 开始。

### 10.6 撤销 —— 这里要诚实(2026-09-15 红队审查加固)

**撤回的边界必须对用户讲清楚,不能模糊**。

| op | 可撤销? | 反向操作 | 备注 |
|---|---|---|---|
| `rename_folder` | ✅ | 改回原名 | 纯改名,B 站没动条目 |
| `move_item` | ✅ | 反向 move | 纯条目移动 |
| `create_folder` | ❌ | 删夹子会连带丢条目,太危险 | **本地不自动撤销** |
| `remove_item` | ❌ | 重新收藏会改变 `fav_time`,有损 | **不可逆** |

执行前的确认界面必须把「**可撤销 N 条 / 不可撤销 M 条**」分开列。

### 10.6.1 红队审查发现:撤回不能回滚"写回期间的外部修改"

**真实场景**:你点了"同步到 B 站" → 写回过程中,你的朋友往同一夹加了新视频 → 你点撤回 → 那个新视频**被一起删了**,因为你不知道。

**这是撤回的隐藏陷阱**,我们必须解决:

**撤回语义 = 「撤销本地本次改动」 + 「写回 B 站的逆操作(如果安全)」**:

1. **写回完成后立即锁定本地状态**:plan 标记为 `synced`,自动锁定本地数据,不再触发增量同步(避免覆盖撤回)
2. **写回前快照**:写回前自动保存 `audit_logs.before_json`(= B 站写回前的状态)
3. **写回后立即增量校验**:写回完成后,自动触发一次目标夹子的增量拉取,**比较 B 站当前状态与写回前快照**:
   - **无外部变更** → 撤回可逆,执行逆操作
   - **检测到外部变更** → 标记「部分可撤回」,只撤回本地已知的部分;**对 B 站侧已变更的部分不操作**(防止覆盖他人改动)
   - 撤回时**明确告知用户**哪些安全、哪些不安全,绝不默默部分执行
4. **删除类操作永不撤回**:`create_folder` / `remove_item` 不提供撤销按钮,UI 显示「该操作已写入 B 站且不可撤销」

**UI 必须显式展示**:哪些可撤回 + 哪些不可撤回 + 哪些受外部变更影响(不能撤回)。
这是 M5 写回 UI 的**硬要求**,不允许"看起来回滚了"的假象。

### 10.6.3 写回前锁定快照(2026-09-15 红队加固 — §10.6.1 的细节)

**写回前**(`执行写回按钮`点击瞬间)必须完成:

```
1. 快照每个将被改动的 B 站夹子:
   - 夹子的 `media_count` 和 `mtime`
   - 夹子内最新 50 条条目的 id 列表(用于检测"写回期间外部新增")
2. 快照存 `audit_logs.detail_json`(已经写回前的状态)
3. 本地数据**锁定**:
   - 同步设置 `locked_until` 时间戳
   - 自动增量同步在 locked_until 之内跳过
   - 写回完成后由用户显式"解锁"或"5 分钟后自动解锁"
```

**写回完成(所有 op 跑完)**立即:

```
1. 触发一次**目标夹子的增量拉取**(只查 mtime,快)
2. 对比拉取结果与 §10.6.1 写回前快照:
   - 一致 → 走"完全可撤回"流程,UI 标"已校验"
   - 媒体数差异(写回期间外部新增/删除) → 标"部分受外部影响",撤回时只回滚本地已知部分
3. 撤回时:
   - 纯改名 / 移动 → 直接逆操作
   - 删除类 → "已写 B 站不可撤回"按钮置灰
   - 受外部变更影响的部分 → UI 显式标"外部已变更,撤回可能不完整"
```

这是 §10.6.1 的具体实现,**写回 UI 必须支持快照-执行-校验-撤回**这个完整生命周期。

### 10.6.2 红队审查发现:长会话 token 失控 + Pass 2 抽样

**Pass 2 全量 3000 条 × 30 条/批 = 100 批,本地 14b 也可能跑几天**。
这不是边缘问题,是真可用性问题:

- **Pass 2 必须抽样**,不跑全量:只对高置信度区间用 AI,**其余按 keyword 规则 + 抽检**
- **断点续跑**:Pass 2 跑一半用户关闭窗口也能继续(session_messages 已记)
- **主动学习策略**:抽 100 个高把握的作为"种子",其余按规则分类,边界再问 AI
- **增量整理**:新收藏走 Pass 2 局部,不动旧条目
- 详细 token 计算与抽样比例在 M4 计划里再细定(spec 这里只标记原则)

### 10.7 删除的三道防线(C5)

```ts
// execute/guards.ts
if (op.kind === 'remove_item') {
  const item = db.items.get(op.itemId)
  if (!item?.invalid) {
    throw new PolicyError(
      `拒绝执行:${item.title} 未标记为失效。非失效收藏一律不允许删除。`
    )
  }
}
```

1. **curator 不生成**非失效条目的 remove op
2. **plan 校验**阶段再挡一次
3. **execute** 阶段最后挡一次 —— 前两层有 bug 也执行不了

### 10.8 失效检测

同步时直接从 `fav/resource/list` 返回的 `attr` / `title` 判断(失效条目 B站会返回标记,
标题通常变成「已失效视频」)。

**不额外调接口探测可用性** —— 那是额外的风控成本,而误判代价只是少删一条,可以接受。
`ponytail: 只信 fav list 的 attr,不做可用性探测;要更准再说。`

**AI 不参与删除决策**。删除是纯粹的「失效内容清理」,由同步时的自动检测驱动。
AI 的职责边界因此很干净:**它只管整理,不管删**。

### 10.9 遇风控的处理

```
立即停止 → plan = paused → 写 events(error,带触发时请求数/间隔)
→ 已完成的操作保留,不回滚
```

**不回滚**是刻意的:回滚 = 更多写请求 = 风控加重。停下来等用户过验证码,是唯一正确的反应。
