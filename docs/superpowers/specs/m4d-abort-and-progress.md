# §9D 可中止的 AI 调用 + 归类进度(2026-09-17)

> 新增节,归属:本文档描述的是**交互与传输层**的变更,影响聊天(§9.0/§11.9)与归类(§9.3)两条路。
> 与 §9C 的关系:不改变任何 §9C 决定(规则匹配、自证、建议不落库全部原样),只给归类这条路的**传输**加进度与中止。

## 9D.0 为什么

一次真实使用暴露了两个缺口(2026-09-16 真机):

> 用户点「按现在这份结构归类」,2976 条进一个请求,界面静默 10+ 分钟 —— 不知道它在跑、
> 不知道跑到哪、也没法停。"是不是卡了"只能靠问。

两个缺口同根:**AI 调用一旦发出,用户就失去了对它的任何控制权** —— 看不到进度,也中断不了。

- **进度**:归类的响应是一次性 JSON,`runPass2` 的 `onProgress(done, total)` 钩子在引擎里
  **存在但路由没接**(§9.3 写了"每批独立、可续跑",但没写界面怎么看到"每批")。
- **中止**:聊天是 SSE 流式,前端 fetch 没接 `AbortController`;归类更是一次性 JSON,
  浏览器端**没有可断的东西**。

## 9D.1 决定

| # | 决定 | 为什么 |
|---|---|---|
| A1 | 归类的传输从一次性 JSON 改成 **SSE**(和聊天同一条技术路线) | 一次性 JSON 结构上不可能有进度。SSE 的解析器前端已经有(`streamMessage` 用的就是),复用 |
| A2 | 每批完成发一个 `event: progress`:`{batch, batches, done, total, ruleCount}`;引擎侧的回调是 **`onBatch`**(除计数外还带本批 `assignments` 与截至本批的 `failedBatches` —— 路由要靠它做每批落库) | `done`/`total` 是条目数,`batch`/`batches` 让界面能显示"第 5/11 批",`ruleCount` 让"规则已接 N 条"在过程里就可见(§9C.3 ③)。失败批次**照旧攒在 failedBatches**,不因单批失败中断整体(§9.3 原语义) |
| A3 | 归类结果**分批落库**:`classifications` 每完成一批就 upsert 一次 | 中断/失败时已完成的批次不白跑。重跑时未完成的批次重算。应用侧的 409 冲突检查(§9B.4)不变,还是比对 `updatedAt` |
| A4 | 结束发 `event: done`(带完整响应形状)或 `event: error` | 与聊天 SSE 的三种 event(delta/done/error)形状对齐,前端一套解析逻辑吃两种流 |
| B1 | 发送按钮**同一枚两态**:空闲 = 发送,流式进行中 = **停止**(方块图标,红色边) | 用户原话:"发送和 stop 是一个按钮"。loading 转圈不可点是对"进行中"的错误表达 —— 进行中恰恰是**最需要可点**的时刻 |
| B2 | 中止 = 前端 `AbortController.abort()` 断开连接;服务端**检测到连接关闭就停**,不再继续调 provider | 不停的话就是"钱花了、结果没人接" —— 归类那次 10 分钟的大请求正是这个形状 |
| B3 | 聊天中断后,**已生成的半截回复落库**,追加"(已中断)"标注 | 半截也是信息:用户看得见它说到哪。全丢是最差的选择。用户消息本来就先落库(§9.0),不动 |
| B4 | 归类中止后,已落库的批次保留(见 A3);抽屉里显示"已中断:N/M 批完成" | 和 B3 同一原则:完成了的不装作没发生 |
| B5 | 服务端对 provider 调用传入 `abortSignal`,来源是 `req.raw.on('close')` | AI SDK 的 `generateText`/`streamText` 接受 signal;断开即抛 `AbortError`,走既有 catch(记一条 warn 日志,不再写 error —— 主动中断不是故障) |

## 9D.2 交互细节

```
聊天抽屉:
  [发送 ▸]  ←→  [■ 停止](红色 danger 边,hover 加亮)
  忙碌中输入框不禁用(用户可以边看边打字,只是发送键变成停止)

归类面板(抽屉内):
  [按现在这份结构归类] ←→ [■ 停止]
  进度行:第 5/11 批 · 已归 1365/2976 条 · 规则已接 274 条
  中断后:已中断:5/11 批完成 —— 已完成的保留,重跑会算剩下的
```

「规则已接 N 条」只在第一批的 progress 里带一次(它来自 Pass 2 之前的规则匹配,本来就该让用户看到这层分工,§9C.3 ③的"如实分栏"在**过程**里就成立,不等结束)。

## 9D.3 不在这一轮

- **归类的分批进度不进 events 表** —— 那是操作留痕(§6/§9B.3),不是实时进度;进度只活在 SSE 里
- **不做"暂停/继续"** —— 中止就是中止;provider 不支持暂停,做了也是假的
- **服务端不提供"断开后继续生成"** —— B2 就是停;断点续跑是 provider 能力,不假装
- **Pass 1(提体系)不加进度** —— 它不可达(§9C.9),等它有入口时再说

## 9D.4 与既有条款的关系

- **取代** §9.3 的"响应是一次性 JSON"吗?**不** —— §9.3 定的是批处理语义(每批独立、可续跑、失败只影响该批),A1–A4 是它的**传输实现**,语义原样
- §11.9 助手的"工作中"状态(AIAssistantIcon 的旋转环)不变 —— B1 的按钮态是抽屉内的局部状态,图标照旧表达全局
- 错误路径不变:provider 抛错照旧 `event: error` + `log.event(level:'error')`;**唯独 `AbortError` 降为 warn**(B5)

## 9D.5 追加(2026-09-17 真机反馈后的三项)

真机用了一次之后暴露的三件事,同根的占两件:

1. **`busy` 必须按事拆分**(`sending` / `classifying` / `applying`):两个「停止」共用一个
   `busy` 时,进行中的那件事会让**另一个**按钮也显示成停止 —— 点了是死键。spec §9D.2
   原样保留,补的只是实现约束:停止键必须指向**自己那件事**的 controller。
2. **「应用到现在的结构」的 loading 只绑 apply 自己** —— 归类进行中它不该转圈(它要等的
   只是归类结果落地,不是整段归类跑完)。
3. **思考过程( reasoning )要可见**:推理型模型(deepseek-flash 实测)会在流里吐
   `reasoning` part,而 provider 只转发 text —— 用户看着几秒到几分钟的空白,以为卡了。
   决定:provider 转发 reasoning;SSE 加 `event: reasoning` 帧(载荷 `{delta}`);气泡里
   折叠显示"思考中…"(点击展开,`--text-dim` 弱化)。**reasoning 不落库、不算正式回复** ——
   它是过程,`chatStream` 的全文与 `(已中断)` 标注语义都不变。没有 reasoning 的模型
   (本地 14b)不发这种帧,前端折叠块整个不渲染。

## 9D.6 追加(2026-09-18:标注那一跑的进度条)

真机反馈:「点击 AI 标注的时候没有进度条啊,一共多少个,现在到第几个」。两处:

1. **帧序列在第一批之前多一帧。** 标注(`POST /api/tags/run`,§9E.2 ④)照抄 §9D 的
   progress 帧模式,而 §9D 的帧**每批完成才发**(A2)—— 第一批结束之前客户端手里没有
   任何数,那一行只能写"已标 0 条"。而分母**开跑前就定了**(池子 = 增量过滤后的条目,
   `runTagging` 的 `total` 就是它,跑中不变;补轮缩的是 pending,不是 total),所以服务端
   在 SSE 头写完之后、`runTagging` 之前**先补发一帧** `{done: 0, total: 池子大小, tagged: 0}`。
   客户端在收到它之前仍可能画不出分母 —— 那是"帧还在路上",不是"不知道那个数"。
2. **除数字行外再加一根进度条。** §9D.2 的如实读数(等宽数字、`num` 不抖)照旧,另加
   antd `Progress` 的确定值长条 + 百分比,两者并存:条用来"一眼看到大概到哪",数字用来
   "准确知道到第几条"。**空池子(`total=0`)百分比给 0** —— `0/0` 是 NaN,会把条画坏。
   条只在跑的时候有(空闲那行说的是"库里标了多少",不是一次跑的进度)。
