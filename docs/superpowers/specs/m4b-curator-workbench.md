## 9B. 整理工作台(2026-09-16 重设计)

### 9B.0 为什么重做

第一版按 §11.5 建的是「左右对置的体系协商屏」:左栏现有结构只读,右栏 AI
建议体系可编辑。真机用下来三个问题:

1. **要在两个世界之间来回翻译**。你改任何东西,都得先在脑子里把"现有夹子的
   样子"映射到"右栏那套平行体系"。用户原话:「这些操作在现有结构上不能完成吗?」
   —— 能,而且应该。
2. **AI 出现在整理页**,和手动整理混在一起,分不清哪条路是哪条。
3. **数字不可信**。当时本地只同步到 23% 的数据(分页 bug,已单独修),
   所以"建议体系 10 个夹子加起来对不上总数"——现在数据可信了,但界面得
   让"改了哪里"看得见。

### 9B.1 核心决定(不可违反)

| # | 决定 | 为什么 |
|---|---|---|
| W1 | **只显示一份结构** —— 你要的样子,不是"建议" | 用户桌上永远只有一份东西 |
| W2 | **快照只读,编辑只写工作副本** | 破了这条「还原」就没意义:改动和 B站 真相混在一起就分不出谁是谁 |
| W3 | **工作副本全局唯一**,不按会话分 | 「现在的体系」是单数。多套竞争方案是旧的错误模型 |
| W4 | **AI 只在对话框**(右下角常驻),整理页不出现 AI | 手动整理没有 AI 也能做完 —— 这是底线 |
| W5 | **「还原」只有一个含义** = 回到本地快照 | "撤销这次写回"是另一件事(M5),必须另起名 |
| W6 | **留痕记的是决策,不是数据变更** | 拖 412 条视频记 412 行日志 = 垃圾,不是留痕 |
| W7 | **AI 的改动和手动改动是同一种东西** | 不允许"AI 特供"的改动类型:同样标记、同样进日志、同样能被还原覆盖 |

### 9B.2 数据模型

```
同步快照(只读,只有 sync 会写)      工作副本(全局唯一一份,编辑全在这)
folders                       ──克隆──▶  work_folders
folder_items                             work_folder_items
     ↑ B站 的样子                            ↑ 你要的样子
```

```sql
-- 工作副本的存在性 + 它基于哪一次同步。
-- CHECK(id = 1) 把"全局唯一一份"钉在数据库层,不靠应用代码自觉。
CREATE TABLE IF NOT EXISTS work_state (
  id          INTEGER PRIMARY KEY CHECK (id = 1),
  -- 克隆那一刻 `sync:lastFull` 的值(上次全量同步完成时间)。
  -- 之后这个数变了 = 整理期间又同步过 = 顶部要提示(§9B.7 约束 5)。
  based_on    INTEGER NOT NULL,
  created_at  INTEGER NOT NULL
);

-- 目标夹子。
CREATE TABLE IF NOT EXISTS work_folders (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  -- 指向快照里的哪个夹子。非空 = 这是现有夹子(可能改了名);空 = 新建的。
  -- 改动标记 ✎ 就是靠它算出来的:origin_id 非空且名字不同 → 改名
  origin_id  INTEGER REFERENCES folders(id),
  name       TEXT NOT NULL,
  created_at INTEGER NOT NULL
);

-- 目标归属(多对多 —— B站 允许一个视频同时在多个夹子里)
CREATE TABLE IF NOT EXISTS work_folder_items (
  folder_id INTEGER NOT NULL REFERENCES work_folders(id) ON DELETE CASCADE,
  item_id   TEXT NOT NULL REFERENCES items(id),
  PRIMARY KEY (folder_id, item_id)
);
CREATE INDEX IF NOT EXISTS idx_wfi_item ON work_folder_items(item_id);

-- 操作日志:一次**操作**一条,不是一行数据一条(W6)
CREATE TABLE IF NOT EXISTS operation_log (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  ts          INTEGER NOT NULL,
  kind        TEXT NOT NULL,      -- 见 §9B.3 枚举
  actor       TEXT NOT NULL,      -- 'user' | 'ai'
  session_id  INTEGER,            -- actor='ai' 时是哪次对话;用来把一次 AI 应用归成一组
  summary     TEXT NOT NULL,      -- 人类可读一句话,界面直接显示
  detail_json TEXT                -- 这次操作碰了哪些夹子/条目
);
```

**`taxonomy_draft` 表保留但不再读写。** 它是按会话存的草稿,与 W3 冲突。
不 DROP 是因为里面可能有你之前的草稿数据,静默删掉不合适。

**夹子顺序:这一轮不做,也不预留列。** 快照(`folders` 表)根本没记录 B站 上的
夹子顺序,所以顺序这件事无法只在工作副本这一侧解决 —— 真要做得先让 sync 把
顺序抓下来。留一个没人写的 `sort_order` 列,只会让人以为它是通的。

**`sessions` / `session_messages` 保留**,角色收窄为**纯聊天记录**。
`classifications` 保留,角色收窄为**AI 的待确认提案**(会话级);
你点「应用到现在的结构」后,它变成工作副本上的若干次操作,提案本身留着做追溯。

### 9B.3 操作类型枚举(一次定全)

以后加功能不该改这张表 —— 所以类型在这里一次定死,UI 可以慢慢做。

| kind | 含义 | 谁会产生 |
|---|---|---|
| `rename_folder` | 给夹子改名 | 手动 / AI |
| `merge_folders` | 把 B 并进 A(**一个动作**,系统内部拆成"移条目 + 删空夹"两步,不暴露给用户) | 手动 / AI |
| `create_folder` | 新建夹子 | 手动 / AI |
| `delete_folder` | 删除夹子(只能删空的) | 手动 |
| `move_items` | 移动:离开原处,放进目标 | 手动 / AI |
| `add_items` | 也放进:保留原处,同时加进目标 | 手动 / AI |
| `remove_items` | 移出夹子(不放进别处) | 手动 |
| `delete_invalid_items` | 删除失效条目 —— **唯一的删除落点**(C5) | 手动 |
| `reset` | 一键还原 | 手动 |

**`move_items` 和 `add_items` 必须分开**:B站 允许一个视频同时在多个夹子里
(你库里现在就有 6 条)。只有一个"拖过去"的动作时系统只能替你猜,
猜错就是悄悄删掉一份归属。

**没有 `apply_ai` 这个 kind** —— AI 应用产生的就是上面那些普通类型,
只是 `actor='ai'`。这是 W7 在数据库层上的落实:AI 的改动在结构上
不可能成为"另一类东西"。

### 9B.4 数据流

```
点「整理」→ 读工作副本
              ├─ 有 work_state 行 → 显示它
              └─ 没有 → 不显示空壳,显示「还没有自己的改动,正在显示 B站 现在的样子」
                        (首次编辑时才克隆,不给用户"开始整理"这一步)

编辑 → 写 work_folders / work_folder_items + 追加一条 operation_log
       改动标记 ✎ ⇥ ✚ ✖ 是**算出来的**(work 与快照比对),不单独存

「一键还原」→ 清空 work_folders / work_folder_items,删 work_state 行
               + 记一条 kind='reset' 的日志

AI 对话框 → 聊 → 提案存 classifications(记下它生成时的 ts)
          → 你点「应用」→ 逐条变成 move_items / add_items 等操作(actor='ai')
          → **应用前查 operation_log 里提案生成之后有没有新条目** ——
             有就说明你在生成期间手改过,明确告诉你是哪几处会被覆盖,
             **不静默覆盖**。静默覆盖是最糟的一种:你以为自己改的还在,其实没了
```

### 9B.5 界面

```
整理                                       [一键还原]   [写回 B站 (M5)]

┌─ 你的收藏夹结构 ─────────────── 64 个夹子 · 改动 3 处 ─┐
│                                                        │
│  🔒 默认收藏夹            2,864   锁:不能改名/删除      │
│                                                        │
│     深度学习                412   ✎ 改名 →「AI/编程」   │
│     机器学习                233   ⇥ 并入「AI/编程」     │
│  ✚  AI/编程(新)            645                        │
│     前端                     88                        │
│                                                        │
│  [ + 新建 ]  [ 把勾选的并成一个 ]  [ 移走勾选的条目 ]   │
└────────────────────────────────────────────────────────┘

  未归类 61 条 · 失效 12 条  →  [去处理]
```

- **夹子和条目在视觉上是两种东西**:夹子是分组头,条目在组里。夹子能改名/合并/删除,
  条目只能移动(取消收藏是 B站 上的事,不在这里)。别让它们长得一样。
- **改动的原值直接看得见**(✎ 旁边就写 `← 「深度学习」`),不用点开、也不悬浮才出现。
  要求是「每个标记一致地能看到原值」—— 内联显示比点开更强:不用操作,也不可能出现
  「有的能展开有的不能」。
- **失效条目单独一栏,「删除」只出现在那一栏。** 「非失效一律不许删」是 C5 红线,
  删除按钮散落各处就守不住了 —— 分不清点的是哪个。
- **「未归类」是唯一的说法**。AI 语境里的「待定」映射到它,不另起一个词。

### 9B.6 不在这一轮

留给后面(表不用动,见 §9B.3):

- **搜索 + 筛选**(2864 条靠滚动管不过来;复用总览页的 FTS5,搜出来要能直接选中操作)
- **改动按夹子聚合显示**(「深度学习 移出 412 条 → 380 条到 AI/编程」,复查用)
- **失效栏的完整 UI**(本轮的删除落点先只留位置)
- **M5 写回**:`diff(工作副本, 快照)` → 操作序列。这个 diff 是 M5 的输入,
  不是为本轮多做的

### 9B.7 硬约束(实现时不许绕)

1. 编辑路径**只能**写 `work_*` 表。任何直接写 `folders` / `folder_items` 的编辑都是 bug。
2. 任何改变工作副本的动作**必须同时**追加一条 `operation_log`。漏一条 = 这个动作无法追溯。
3. AI 应用产生的日志 `actor='ai'`,其余 `actor='user'`。除此之外**不允许**对 AI 来源的改动做特殊处理。
4. 锁定的夹子(§9B 引用的默认收藏夹)在工作副本里也不能改名、不能删除;
   只能移动它的条目。复用锁定夹子时名字必须原样 —— §9.1.1 已有这条校验。
5. `work_state.based_on` 之后如果又同步过,顶部必须提示(不阻断,但不能不吭声)。

### 9B.8 测试

| 测什么 | 为什么 |
|---|---|
| 克隆出来的工作副本与快照逐行相等 | 克隆错了后面全错,而且不会报错 |
| 改动标记的计算:改名/合并/新建/删除 各一例 | 标记是算出来的,算错就等于给用户看假信息 |
| 每次编辑都产生且只产生一条日志 | 漏记 = 无法追溯;多记 = 日志淹掉 |
| 「还原」后 work_* 全空、快照一行没动 | W2 是地基,破了「还原」就没意义 |
| `move_items` 与 `add_items` 的归属差异 | 猜错就是悄悄删掉一份归属 |
| 删除非空夹子被拒 | C5 红线 |
| AI 应用的改动与手动改动产生同样的日志结构 | W7 |

**只手动验证**:2864 条真实数据上的界面手感、改动聚合视图的可读性。
