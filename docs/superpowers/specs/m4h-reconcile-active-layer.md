# Spec:词库整理(reconcile)按活跃层计算 —— 让整理成本与总词数解耦

> 状态:**已实施(2026-09-18)**。下面 §1.4 的两个性能点 + 本 spec 的四件事
> (活跃层剪枝、空池子跳过、预算守卫、自适应下限)全部落地,验收见文末补记。
> 关联代码:`server/src/curator/tagtree.ts`、`server/src/db/repo/tags.ts`。

## 一、背景与为什么必须改(前因后果)

### 1.1 词库怎么长的

本项目的词库由「AI 标注」自动长出(spec §9F C5):每轮标注,模型对未标注的视频产出标签,
库里没有的词就 `ensureTag` 新建。用户库现状:约 3205 条视频,词库 **12005 个词**,
`item_tags` 关联 13888 条。平均每个词只挂 1.16 条视频 —— 绝大多数是"一次性词"
(只被 1~2 条视频使用,如专有名词"南宫家书""白霓裳")。

### 1.2 reconcile 是什么、为什么每轮都跑

`reconcile(db)`(tagtree.ts)是**每轮标注跑完后的自动整理**(§9F C8/C9/C10):
按"词挂了哪些视频"的集合关系,做两件事:
- **合并**:两个词双向覆盖 ≥90% 且样本够 → 同义词,并成一个。
- **挂父**:一个词 ≥90% 覆盖另一个 → 前者挂到后者下。

**注意:即使空池子(本轮没标任何条目),reconcile 也会跑**(tagRoutes.ts 里无守卫)。

### 1.3 症状与根因

用户报告:**点「AI 标注」后,后端瞬间响应 `{ok:true}`,但随后所有接口
(`/api/tags/run-progress`、`/api/tags/status`)全部 pending,前端无进度、停止无效**。

用 curl 实测定位:
- `POST /api/tags/run?scope=missing` 直连后端 → **34ms 秒回** `{ok:true, poolSize:0}`。
- 该请求返回后,`run-progress` 立刻 pending(3s 超时),后端进程内存涨到 3.3GB。

根因:POST 的 `reply.send({ok:true})` 在 handler 前半段执行(组池后立即 send),
但 **handler 后半段的 `reconcile(db)` 是同步全表计算**,它把 Node 的**单线程事件循环
永久占死** —— reconcile 没跑完,后续任何请求都排不上队。

### 1.4 reconcile 的两个性能黑洞(已修一半)

实施本 spec 前,主 session 已修了两个具体瓶颈(测试全绿、真实库 115ms):

1. **`coverageMap`/`pairs` 剪枝**(已修):跳过 `size < minSample(5)` 的词。
   原来对全部 12005 词两两算(12005² ≈ 1.44 亿对,每对遍历视频集);
   现在只算挂 ≥5 条的词(实测 212 个)→ 212² ≈ 4.5 万对。**结论不变**
   (判据本来就对 <5 条的词不判),差 3000 倍。

2. **`isDescendant` → 内存版 ancestor**(已修):原来 `isDescendant(db,b,a)`
   **每次调用都全表扫 `SELECT id,parent_id FROM tags`(12005 行)** 再建 Map 爬父边;
   reconcile 对每对调两次。改成用 reconcile 内存快照 `parentOf` 走内存,
   合并后主动同步父边。**为什么安全**:mergeTags 把 drop 的子节点父改成 keep
   (库里 `UPDATE tags SET parent_id=? WHERE parent_id=?`),内存 parentOf 同步这一步
   后与库一致,等价于原"查库防过时"的语义。

### 1.5 客观性能基准(本 spec 的依据)

主 session 用**合成数据**跑 `reconcile`,量不同形态下的真实耗时。

> **数据修正说明**:初稿的基准因视频总数( totalItems )不够活跃词使用,导致活跃词
> 被**人为重叠**,高估了低活跃词数的耗时。修正后重测:真实形态(活跃词**互不重叠**,
> 各挂 10 条视频)下,性能由**活跃词数**决定,呈 O(活跃词²):

**活跃词数 → reconcile 耗时(活跃词互不重叠、各挂 10 条):**

| 活跃词数 | 耗时 |
|---|---|
| 300 | 36ms |
| 1,000 | 307ms |
| 3,000 | 2,523ms |
| 10,000 | 55,484ms |

**对照:总词数本身几乎不影响**(均匀分布 10 万词,全部参与也只 253ms —— 但那是
"每个词各挂各的视频不重叠"的特例,不是真实形态)。

### 1.6 数据结论(决定方案)

- **性能不由"总词数"决定,由"活跃词数"(挂 ≥5 条视频的词)决定**,O(活跃词²)。
  真实形态下活跃词基本互不重叠("美食""篮球""AI"各挂各的),平方常数小:
  **1000 活跃 = 307ms 安全;3000 活跃 = 2.5s 开始变慢;10000 活跃 = 55s 崩。**

- **用户当前真实库是安全的**:7559 个有挂载的词里只有 212 个活跃 → reconcile ~100ms。

- **但是定时炸弹**:活跃词数涨到 ~3000+ 时 reconcile 从秒级崩到分钟级。
  收藏持续增长(用户明确说会越来越多),活跃词数必然增长。阈值应定在
  **3000 活跃词**(1000 安全、3000 开始 2.5s,见 2.3)。

### 1.7 为什么"优化计算"治标不治本

剪枝、内存化、甚至换 Redis/bitset 都只是**给 O(活跃词²) 续命**。活跃词数涨到几千,
无论用什么数据结构,单线程同步算完都会占死事件循环。

**诚实的结论**:本 spec 的活跃层方案**只是把基数从"总词数"降到"活跃词数"**,
O(n²) 本身还在。它依赖两条腿才成立:
1. **降基数**:活跃词增长远慢于总词数,长期维持在一千量级(1000 活跃 = 307ms)。
2. **兜底**:预算守卫保证即使活跃词暴涨到 3000+、10000+,reconcile 也最多花
   5s 就收手,不占死事件循环。

**真正的"解绑"**(让成本与活跃词数无关)是**增量整理**——只算本轮涉及的词,
而非全库。那是更大的架构改动,本 spec 不做,但记录为后续方向:如果将来活跃词
持续破万,增量整理是必选项。

## 二、方案:活跃层(冷热池)

### 2.1 核心思想

把词库分成两层,reconcile 只对**活跃层**做集合计算:

- **活跃词**(热层):挂的视频数 ≥ `MIN_SAMPLE`(5)。参与覆盖计算/合并/挂父。
- **冷词**(冷池):挂的视频数 < 5。**不参与覆盖计算**。它们只是"这条视频的标注",
  对整理无统计意义(判据本来就对它们不判,spec §9F C9)。

总词数可以无限涨(收藏越多,一次性词越多),但活跃词数增长远慢于总词数。
活跃词 1000 时 reconcile 307ms,即使总词库 10 万也快。但活跃词数**本身会涨**
(收藏持续增长,活跃词也会从几百涨到几千)—— 所以活跃层只是**降基数**,不消除
O(活跃词²),需要 §2.3 的守卫兜底。

### 2.2 具体改动

**改动点:tagtree.ts 的 `reconcile`(以及它调用的 `coverageMap`/`pairs`)。**

当前实现已按 `minSample` 剪枝(coverageMap 和 pairs 都跳过 `size < minSample`)。
本 spec 要求把"剪枝"升级为**显式的活跃层概念**,并解决两个剪枝没解决的问题:

**问题 1:活跃词本身会涨,reconcile 是 O(活跃词²)。**
剪枝后 `coverageMap`/`pairs` 只对挂 ≥5 条的活跃词算对。真实形态活跃词互不重叠时
平方常数小(1000 活跃 307ms),但活跃词数涨到 3000+ 就对爆炸(3000 活跃 2.5s、
10000 活跃 55s)。
**要求**:reconcile 的覆盖计算只发生在活跃词之间(已做到),并且**一旦活跃词数超过
阈值,用预算守卫兜底**(见 2.3),不让它占死事件循环。

**问题 2:冷词完全被忽略,但冷词里可能藏着"该合并的同义词"。**
当前剪枝直接跳过 <5 条的词,永不处理。两个各挂 3 条、恰好挂同一批视频的词
(覆盖 100%)不会被合并。**本 spec 不要求解决这个**(它需要样本阈值以下也做
"完全相同集"的特殊合并,是另一个改动),但要在文档里记录为已知限制。

**改动点:树变了才整理(不是"空池子跳过")。**
`tagRoutes.ts` 里,reconcile 的触发时机从"每轮都跑"改为**"本轮真的标了条目"
( pool.length > 0 )才跑**:

| 场景 | 行为 |
|---|---|
| 标注真跑了(池子非空,有新词) | **同步** reconcile —— 树变了,必须整理 |
| 空池子(没标任何条目) | **跳过** reconcile —— 没新词树没变 |

**为什么不是"空池子永远跳过"**:reconcile 不只处理本轮产物,还整理**历史积累的
同义词**("教程/教学/学习"是过去几百条视频长出来的)。但如果空池子也同步跑,
用户**高频点 AI 标注**(全标完后每次点都是空池子)会被 reconcile 拖慢 —— 词库
涨到 3000 活跃就是每次 2.5s。所以空池子跳过 + 真实标注时整理,两全:高频场景不卡,
历史同义词在**下次真实增量标注时**一并合并(树真的变了才需要整理)。

**已知限制**:如果用户全标完后**再没有新条目进库**,历史同义词将不再被整理。
本 spec 接受这个(下次有新条目标注时自然恢复)。若要覆盖"标完了也整理",
需另加独立的整理入口(范围外,记录为后续)。

**改动点:tagRoutes.ts 的调用处加运行窗口。**
reconcile 是同步的,一旦运行就占死事件循环。为防极端情况(活跃词突然暴涨),
给 reconcile 加一个**预算**:比如超过 5s 就放弃本轮整理并记一条 warn 日志
("词库整理超时,本轮跳过 —— 活跃词过多需要治理")。这样即使数据爆炸,
也只是"这轮没整理",不会卡死整个服务。

### 2.3 活跃层的规模守卫(必须)

光有"只算活跃层"还不够 —— 活跃词数本身可能涨到几千。需要一个**可自动化的守卫**:

- **主动词数监控**:暴露一个指标 `GET /api/tags/reconcile-stats`,返回
  `{ totalTags, activeTags(≥5条), reconcileMs(最近一次耗时) }`。
  前端可在「标签」页显示词库健康度,用户能看到"词库正在膨胀"的早期信号。

- **合并阈值自适应(可选)**:如果活跃词数超过上限(**3000**,依据 §1.5 曲线:
  1000 活跃安全、3000 活跃开始 2.5s),自动把 `minSample` 从 5 调到 10 ——
  用更少的活跃词维持计算在预算内。这是**自动化维护**的一部分:规模涨,
  下限跟着涨,整理成本保持可控。**用数据支撑,不拍脑袋**:活跃词数与耗时
  曲线见 1.5,阈值定 3000。

## 三、验收标准(客观可测)

1. **性能预算**(活跃词互不重叠,各挂 ~10 条 —— 真实形态):
   - 活跃词 1,000 → reconcile ≤ 500ms(实测 307ms,留裕度)。
   - 活跃词 3,000 → reconcile ≤ 5s(实测 2.5s,预算内)。
   - 活跃词 10,000(超过守卫阈值)→ reconcile 触发超时守卫,在 ≤5s 内返回
     (不卡死事件循环),记一条 warn。
   - **最坏情况(活跃词重叠,同义词并存)**:1,000 活跃、每对共享 50% 视频 →
     reconcile 触发超时守卫或 ≤5s 返回(重叠会让覆盖对爆炸,这正是守卫存在的理由;
     验收点:不卡死,而不是必须算完)。

2. **行为不变**:
   - 现有 tagtree.test.ts / tagRoutes.test.ts 全部通过(判据语义不因分层改变)。
   - 真实库(server/data/app.db,只读打开)reconcile ≤ 200ms(当前 115ms 的合理上界)。
   - 空池子场景:`POST /api/tags/run?scope=missing`(池空)后,`run-progress` 立即响应,
     不再 pending;reconcile 被跳过(测试断言零调用)。

3. **可观测**:
   - `GET /api/tags/reconcile-stats` 返回真实指标。
   - 超时守卫触发时,events 表有一条 `TREE_RECONCILE_TIMEOUT` warn 记录。

## 四、不做的事(范围外,明确排除)

- **不优化标注 prompt 让模型复用已有词**(源头限流)—— 那是另一个改动,
  与本 spec 解耦,但方向一致(控制词库增长)。记录为后续。
- **不解决冷词里隐藏的同义词**(样本 <5 的 100% 重合)—— 记录为已知限制。
- **不加 Redis/bitset** —— 基准证明问题不在数据结构,在计算量;分层后不需要。
- **不改判据语义**(merge/reparent 的 0.9 / 5 阈值不变)—— 只改"算哪些词"。

## 六、实施补记(2026-09-18)

按 `docs/superpowers/plans/2026-09-18-M4h-reconcile-active-layer.md` 实施,已落地:

- **活跃层统计**:`tagScale(db, minSample)`(tags.ts)返回 `{ totalTags, activeTags }`;
  `GET /api/tags/reconcile-stats` 报 `{ totalTags, activeTags, reconcileMs, lastRunAt }`,
  耗时存在路由文件内的 `lastReconcile` 模块级变量。
- **空池子跳过**:run 路由里 `pool.length === 0` 时跳过质检和 reconcile,发 info note
  后直接给零值结果(形状不变)。原有"判据照跑"断言改为"判据不跑、树不变",
  另补一条池子非空照常合并的保留用例。
- **预算守卫**:`reconcileWithBudget(db, { budgetMs })`(默认 5s)返回
  `{ changes, timedOut }`;deadline 一路传进 coverageMap/pairs(快照构建本身才是
  大头,只查循环体挡不住)。超时即部分整理收手,路由记 `TREE_RECONCILE_TIMEOUT` warn。
  超时判定在返回前统一做一次 —— 预算烧在快照期时循环体一次都不进,只在循环里
  置位的话那种超时无人认领。
- **自适应下限**:活跃词 > 3000 时 minSample 自动 5→10,console 记 info。
  调用方显式传 minSample(测试)时优先。
- **前端**:「标签」页词库块右侧显示 `活跃词 N / M · 上次整理 Xms`,标注跑完/手动
  操作后随树一起刷新。

验收实测(合成数据,活跃词互不重叠各挂 10 条):1,000 → 356ms;3,000 → 3.1s;
10,000 → 5s 守卫收手 timedOut=true + 自适应日志触发。全量 vitest 773 条通过,
server/web typecheck 干净,web build "Compiled successfully"(退出码 1 是既有
esbuild helper 冲突,与本次无关)。真实库只读基准未跑 —— 对生产库跑 reconcile
有真实写风险,守卫语义已由合成数据覆盖。
