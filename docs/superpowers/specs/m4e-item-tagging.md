# §9E 条目 AI 标注(ai_tags)—— 给归类补上语义信号(2026-09-17)

> 新增节。前置:§3(模型接入)、§9C(规则)、§9D(可中止 AI 调用)。
> 与 §9C 的关系:**不改变任何 §9C 决定** —— 标注是给归类/规则**补充信号**,分类的权威仍是
> 规则(字面匹配)+ AI 归类(语义),标注只是让后者看得更清。

## 9E.0 为什么

真实使用暴露的边界(2026-09-17,和用户的对话):归类时模型只能看到
`标题 + 简介前 120 字 + UP + 时长`(§9.3)。"AI 动画"是教程还是娱乐、"AI 漫剧"和"AI 动画"
差在哪 —— 这些**语义判断**靠一个批量 prompt 里被摊薄的注意力,猜错过(§9C.0 的事故)。

用户的方案(2026-09-17,原话):**"通过 AI 对名字进行分析,得出结论:这是一个什么类型的视频,
然后再作为信息补充,给到 AI 进行分类"** —— 两段式:先标注、再归类。

**为什么两段式比"归类时顺便看"强:**
1. **一次标注,永久复用** —— 标签落库;归类可以反复重跑,不用每次重新读全库
2. **逐条注意力** —— 归类一个 prompt 摊在 68 条上;标注单条独占
3. **给规则补语义字段** —— "kind 含教学"是语义结论,规则能字面匹配它(将来)
4. **可见可审** —— 标签是人能抽查的;"这条标错了"比"归类错了"容易发现

**实测依据(2026-09-17,用户本机):** `qwen3-4b-instruct-2507`(本地,已装,2GB,262K 窗口)
给库里真实条目打标:JSON 干净、kind 听约束(教学/娱乐分对了 Stable Diffusion vs 玄幻)、
**8 条 0.79 秒 → 全库 3250 条 ≈ 5 分钟,零成本**。deepseek-flash 的 reasoning 实测 316 字符
( §9D.5 已可见),证明推理型模型做标注也行 —— 但**本地免费那个就够**。

## 9E.1 决定

| # | 决定 | 为什么 |
|---|---|---|
| C1 | 标注结果写 `items.ai_tags` / `items.ai_checked_at`(**现成的列,零迁移**) | C8 的宿命:建表时预留,"AI 产生的事实"与同步列物理隔离。格式:`JSON.stringify({ tags: string[], kind: string })` |
| C2 | 标注模型走 `readLlmSettings(db, 'tag')`,**没配自动回落主模型** | §3 的用途分组已就位(打标模型卡片);本地 4b 免费快,flash 也行 |
| C3 | **kind 是受控枚举**:`教学 / 娱乐 / 评测 / 资讯 / 工具 / 其它`,由提示词约束 + 服务端校验(不在枚举内 → `其它`) | 用户实测发现不受控的 kind 会产生"教程/教学/学习"同义词,规则没法用 |
| C4 | 批量标注,**逐条覆盖断言**:一次喂 N 条,输出少于 N 条 → 缺的条目单独补一轮(最多 2 次) | 用户实测:让它标 8 条只吐了 4 条就停。不补的话静默漏标 |
| C5 | `renderItem` 加一行 `AI标签:tag1·tag2·[kind]`(**有才写,没有不占行**) | 归类时模型同时看到原始数据 + 标签;没有标注的条目和今天完全一样 |
| C6 | Pass 2 提示词声明:**"AI标签是参考,原始标题/简介是事实;冲突时以原始数据为准"** | 标签会错(没有自证机制 —— 见 9E.4),原始数据是兜底。防止模型盲信错误标签 |
| C7 | **标注可重跑、可增量**:默认只标 `ai_checked_at IS NULL` 的条目;UI 提供"重新标注全部" | 新收藏来了只标新增;换模型/改词表后可全量重刷 |
| C8 | UI:标注入口在「规则」页(它服务于归类质量);进度用 §9D 的 progress 帧模式 | 标注存在的理由就是让归类更准,和规则/试跑放一起;打断可续(ai_checked_at 天然是断点) |

## 9E.2 运行方式

```
点「AI 标注」(规则页)→
  ① 读 readLlmSettings('tag')  → 没配回落主模型(前端提示当前用哪个)
  ② 找 ai_checked_at IS NULL 的条目(增量);「重新标注全部」则全量
  ③ 批量(16 条/批,§3 的 batchSize 口径)→ 每条产 {tags[2..4], kind}
     → 校验 kind ∈ 枚举(否则其它)、tags ∈ 2..6 个、非空
     → 写 ai_tags / ai_checked_at,**逐批落库**(§9D A3 的既有模式)
  ④ 每批发 progress 帧({done, total});可中止(§9D B2 全套);
     中断后已完成的不白跑(ai_checked_at 就是断点)
```

## 9E.3 与既有条款的关系

- **C8(硬约束)**:同步**永不**写 `ai_tags` / `ai_checked_at` —— 这正是它们被物理隔离的理由
- **§9C 的规则引擎不动**:`RuleField` 本轮**不加** `tag` 字段(R2 的"三个字段"暂不破)——
  标签先通过 renderItem 进入归类这条语义路;规则层的第四字段等标签质量被用户认可后再说
- **§9D 的传输/中止/进度模式原样复用**(SSE + progress + stop 按钮),**不新发明**
- chatStream / 聊天**不带标签** —— 聊天是结构对话(§9C.5 c),塞 3250 条标签只会挤掉对话预算

## 9E.4 明确接受的天花板

- **标签没有自证机制**(§9C.5 的自证只对关键词建议成立)—— 所以标签**永远是补充信号**:
  C6 的"原始数据为准"是结构性的防盲信,UI 上标签可见可抽查
- 分批标注的**跨批一致性**靠 kind 枚举(提示词给出定义),不保证跨批的 tags 词形完全统一 ——
  语义近似可接受,规则层(若将来用)按"包含"匹配
- 「重新标注全部」会**覆盖**旧标签(不再保留)—— ai_checked_at 记录的是最后一次标注时间

## 9E.5 不在这一轮

- **规则加第四字段 `tag`**(改 R2)—— 等标签质量验证后再说
- **B站官方标签同步**(view 接口有 `tags`,需授权 + 3250 次限速请求 + schema 加列)——
  与 AI 标签互补;做了之后可作对照
- **简介放开 120 字截断** —— 独立小改,和标注无关
- **标注质量评估 UI**(抽查面板)—— 先靠规则页的命中数和归类理由观察
