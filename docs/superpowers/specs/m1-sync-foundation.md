## 7. 同步引擎

### 三级增量

```
启动同步 = ① 拉收藏夹列表
         → ② 对比 media_count / mtime,挑出变化的夹子
         → ③ 只对变化的夹子分页拉条目(20 条/页)
```

日常情况**十几秒完成**;首次全量 3000 条约 **3~6 分钟**,可中断、可续跑
(游标写在 `sync_state`)。

### ✅ 实测确认:同步路径不需要 wbi

`fav/folder/created/list-all` 和 `fav/resource/list` **都不需要 wbi 签名**(实测验证)。
这意味着同步引擎:

- 不需要 `nav` 接口、不需要 mixinKey、不受每日密钥轮换影响
- 风控暴露面显著更小 —— 这两个接口本身就很宽容(实测连续请求全部通过)
- `BiliClient.get(..., { signed: false })` 即可

### ⚠️ 坑 1:`list-all` 的 `type` 参数似乎被忽略

实测:用 `type=11`(视频)和 `type=21`(文章)各请求一次,返回**完全相同**
(都是 64 个夹子 / 3480 条)。**不能用 `type` 区分视频夹和文章夹。**

M2 必须解决这个 —— 候选方案:逐夹调 `fav/resource/list` 看条目的 `type` 字段
(`2`=视频 / `12`=文章)来判定夹子类型。这是**同步引擎里唯一还没定论的地方**。

### ⚠️ 坑 2:抓不到失效条目样本

两次采样的 `attr` 都是 `0`。失效条目用什么标记仍未确认。
M2 首次全量同步时统计 `attr` 的取值分布即可确定 —— 不需要专门探测。
`ponytail: 只信 fav list 的 attr,不做可用性探测;要更准再说。`

### 增量判据(反直觉的坑)

`media_count` 可能包含已失效视频,所以**不能**用 `media_count !== 本地条数` 判断 ——
会永远不相等,导致每次都全量重拉。

```ts
needsSync = folder.mtime !== local.mtime || localCount < folder.media_count
```

## 8. B站客户端与风控

### 风控策略

### ⚠️ 已实测确认(2026-09-14)

以下结论**已通过真实 API 请求验证**,不是推测:

| 结论 | 证据 |
|---|---|
| **wbi 签名算法**正确 | `space/wbi/arc/search` 签名后从拦截改为 `code 0` |
| **`buvid3` 是必需且充分的一环** | 同上:仅补 `buvid3` 即通过 |
| **wbi 签名必要但不充分** | 只签名不带 `buvid3` → 仍 `-352 风控校验失败` |
| `fav/folder/created/list-all` **不需要 wbi** | 不签名直接 `code 0` |
| 部分接口额外要求 `SESSDATA` | `space/wbi/acc/info` 补了 `buvid3` 仍 `-352` |

**这修正了一个重要假设**:原设计把 wbi 签名当作主要防线,实际上**风控指纹(`buvid3`)同等重要**。
签名对了但不带 `buvid3`,照样吃 `-352`。

### 措施

| 措施 | 说明 |
|---|---|
| `buvid3` / `buvid4` | 启动时从 `x/frontend/finger/spi` 获取并缓存到 `settings`。**必需** |
| 登录态 cookie | `SESSDATA` + `bili_jct`。部分接口(如账号信息类)在此基础上才放行 |
| wbi 签名 | 参数排序 → urlencode → 剥 `!'()*` → 拼 mixinKey 做 md5 得 `w_rid`。mixinKey 由 `nav` 的 img_key+sub_key 经 **64 位置换表** 生成,**每日轮换**,需按天缓存 |
| 限速 + 抖动 | 读 1200ms ± 400ms;写 2500ms ± 1000ms。**不用固定间隔**,那是机器人特征 |
| 全局串行 | **不发任何并发请求**。单账号并发本身就是风控特征 |
| 真实 UA + Referer | `Referer: https://www.bilibili.com` |
| **不做代理池 / 多账号** | 自己的号平时不在那些 IP 登录,代理反而是异常信号 |

**wbi 签名实现要点**(已实测):

```ts
const MIXIN_TAB = [46,47,18,2,53,8,23,32,15,50,10,31,58,3,45,35,27,43,5,49,
  33,9,42,19,29,28,14,39,12,38,41,13,37,48,7,16,24,55,40,61,26,17,0,1,60,51,
  30,4,22,25,54,21,56,59,6,63,57,62,11,36,20,34,44,52];

// raw = img_key + sub_key (各 32 位 hex,共 64 位)
const mixinKey = MIXIN_TAB.map(i => raw[i]).join('').slice(0, 32);

// 签名
const wts = Math.round(Date.now() / 1000);
const query = Object.keys({...params, wts}).sort()
  .map(k => `${encodeURIComponent(k)}=${encodeURIComponent(String(params[k]).replace(/[!'()*]/g, ''))}`)
  .join('&');
const w_rid = md5(query + mixinKey);
```

**核心架构性选择**:本地存完整缓存,AI 的全部整理计算都在本地数据上跑,**只有最终要
落地的写操作才走 API**。这让请求模式从「爬虫」变成「偶尔同步一次的个人客户端」。

### 错误分级与响应

| 错误 | 含义 | 动作 |
|---|---|---|
| `-412` / `-352` | 触发风控 | **立即停止整个队列**,不重试。标记 paused,提示去过验证码 |
| `-101` | 未登录 | 提示重新填 cookie |
| 网络错误 / 5xx(读) | — | 指数退避重试 3 次 |
| 网络错误 / 5xx(写) | — | **不自动重试**,标记 failed 交给用户(C4) |
| LLM JSON 解析失败 | — | 重试 2 次,仍失败则该批标记失败,其余继续 |

**风控越界的唯一正确反应是停下来,不是重试。** 这条写进客户端层,业务层拿不到重试的机会。

### 一个重要的 API 事实

`x/v3/fav/resource/deal` 是**移动**语义(带 `old_media_id`),一步完成,不是「先删再加」。
所以 move 是**单次原子调用**,省一半请求,风控上也更安全。
