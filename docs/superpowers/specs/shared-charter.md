## 1. 背景与目标

用户有 1000~5000 条 bilibili 收藏(视频 + 专栏文章),散落在几十个收藏夹里。
现有工具的问题:只有手动整理,且收藏夹一旦乱了就再也理不清。

**本项目的目标**:做一个本地 Web 应用,由 AI 扮演「管家」角色,主动提出整理方案,
用户审阅修改后,把结果**写回 bilibili**。

### 核心用户诉求(按优先级)

1. **AI 主动提建议**,但用户保留**建议权** —— 双方都能提,AI 要听得懂自然语言指令
2. **每次启动能全量同步**当前所有收藏
3. 整理结果**同步到 bilibili** —— 这不是本地收藏夹管理器,bilibili 是唯一真相源
4. 操作面:**新建收藏夹 / 移动条目 / 删除条目**(移动是最高频)
5. 删除**仅限失效内容**

## 2. 硬性约束(不可违反)

| # | 约束 | 落实位置 |
|---|---|---|
| C1 | bilibili 是唯一真相源,本地 SQLite 只是缓存 | 所有写操作以 API 结果为准 |
| C2 | 所有写操作必须经过 Plan,没有「直接执行」路径 | 建议模式在代码层的落实 |
| C3 | 所有 API 请求必须经过限速器,业务层拿不到裸 fetch | `bilibili/client.ts` |
| C4 | **写操作永不自动重试** | 重试是加重风控的最快方式 |
| C5 | **非失效收藏一律不允许删除** | 三道防线,见 §10.7 |
| C6 | LLM 输出必须结构化 + 可重试 | 本地小模型的 JSON 一定会坏 |
| C7 | 执行引擎必须可中断、可续跑、可撤销 | `executions` 表 |
| C8 | 同步字段与 AI 派生字段物理隔离,永不互相覆盖 | `items` 表设计 |
| C9 | 日志脱敏在唯一入口做,业务代码没有漏的机会 | `logger/redact.ts` |
| C10 | **凭证只从 UI 进,永不要求用户编辑文件** | `/settings` → SQLite `settings` 表,见 §11.7 |
| C11 | 客户端只向 bilibili 域名发请求 | cookie 安全底线,即便将来接第三方服务也不放开 |

### 关于 C8 的说明

这是这类工具最经典的翻车点:重同步会把你花 20 分钟跑出来的 AI 标签全部洗掉。
所以 `items` 表里同步只写同步字段,AI 只写 `ai_*` 字段,两组永不交叉。
