## 9C. 规则(整理的核心资产)

### 9C.0 为什么

用户的洞察(2026-09-16),从一次真机事故里长出来的:

> 4 条明确的「AI 大模型 / Agent 教程」被归进了「**黑神话**」(一个游戏夹子),而且全标
> 90% 置信度。**这本身是个信号 —— 出问题的是规则,不是那 4 条视频。**

真机验证(拿真 Ollama 跑完整链路)确认了根因:`run-pass-2` 改成从工作副本取体系之后,
每个夹子的判定依据是**空的** —— 模型只能看见 63 个夹子**名字**,于是按名字瞎猜,
而且自信地错(比"拿不准"更糟)。

结论:**bilibili 有夹子但没有逻辑**。夹子只是个筐,谁进去全靠手。而"谁该进去"是判据 ——
判据只能存在本地。**这是本产品唯一比 B站 多的东西,是核心资产。**

### 9C.1 核心决定(不可违反)

| # | 决定 | 为什么 |
|---|---|---|
| R1 | 规则是**结构化可执行的**,不是一段自由文本 | 能执行才叫资产,否则只是 prompt。而且只有能执行才算得出「命中几条」—— 那是调规则时唯一有用的反馈 |
| R2 | 字段**只留三个**:`title` / `intro` / `upper` | 不加正则、不加与或非、不加权重。表达力换"你一眼看懂它在干什么" |
| R3 | 条件之间 **OR**,一个夹子一组条件 | 覆盖「标题含 A 或 B 或 简介含 C」这种最常见的写法。再复杂就归 AI |
| R4 | 一条条目**同时命中多个夹子 → 都归** | B站 本来就支持一条视频在多个夹子里。命中即成员,不用记"谁优先" |
| R4b | **AI 仍然只给一个主归属**(§9.3 不变) | 因为**两组条目不相交**:规则命中的那些根本不进 AI 的输入(§9C.3 ②)。所以"规则多归属"和"AI 单归属"**不可能撞在同一条上** —— 这不是不对称,是两段互不重叠的处理。反过来说:同一条条目要么由规则决定(可多个夹子),要么由 AI 决定(一个主归属),永远不会同时被两边处理 |
| R5 | **规则先跑,AI 只处理剩下的** | 规则命中的部分 0 token、且**可复现**;AI 只做规则吃不准的语义边界 |
| R6 | **AI 发现体系不合理时给建议,不只是硬塞** | AI 的输出有两个通道:归类 + **规则建议**。后者才是"AI 主动提建议"(§1 的核心诉求) |
| R7 | **AI 的建议必须自证**,验证不过就丢 | 见 §9C.5 —— 防幻觉的关键一步,和 §9.1.1 同一思路 |

### 9C.2 数据模型

```sql
-- 规则挂在**工作副本的夹子上**。一个夹子一组条件(PRIMARY KEY 就是 folder_id)。
--
-- 刻意**不做** `ALTER TABLE work_folders ADD COLUMN`:那张表已经存在,
-- 加列要走迁移;而新建一张表用 CREATE TABLE IF NOT EXISTS 就够了,
-- 而且 ON DELETE CASCADE 顺手解决"删夹子/一键还原时规则跟着走"。
CREATE TABLE IF NOT EXISTS work_folder_rules (
  folder_id       INTEGER PRIMARY KEY REFERENCES work_folders(id) ON DELETE CASCADE,
  conditions_json TEXT NOT NULL,
  -- 'ai' | 'user' —— 谁写的。界面上一眼看出这是谁的主意(§11.2 颜色是信息)
  origin          TEXT NOT NULL,
  updated_at      INTEGER NOT NULL
);
```

`conditions_json`:

```jsonc
[
  { "field": "title", "any": ["Python", "JS", "Rust"] },   // 标题含任一个
  { "field": "intro", "any": ["算法", "数据结构"] }         // 或 简介含任一个
]
```

**克隆时不带规则**:`ensureWorkcopy` 从快照克隆夹子,而 B站 上没有规则这个概念 ——
规则是**你**的资产,不是 B站 的,所以新副本的规则表是空的。

### 9C.3 运行方式

```
点「按现在这份结构归类」
  ① 规则匹配 —— 0 token,一次全表扫描
     每条条目 × 每个夹子的规则 → 命中的直接归(可命中多个,都归,见 R4)
  ② 剩下的分批交给 AI —— 批大小仍按 contextWindow 算(§3)
     喂给模型的体系里,每个夹子带:
       · 它的规则(有的话)
       · **没有规则的夹子,带它里面已有的 3 条标题当例子**
  ③ 结果如实分栏:规则覆盖 X 条 · AI 归了 Y 条 · 未归类 Z 条
```

**②里"带已有标题"是必须的**,理由就是 §9C.0 那次事故:一个没有规则的夹子,
模型只看名字就会瞎猜。给它三条标题,它立刻知道那夹子是放什么的。

**规则让归类可复现**:规则是确定性的 —— 改一条规则、重跑、结果可预测。
不再有"模型每次心情不同"。

### 9C.4 界面

**`/rules` 是**和「整理」同级的顶级 tab**,不是 `/curator` 底下的子 tab。**

导航:`总览` · `整理` · **`规则`** · `授权`。

为什么不挂 `/curator` 底下:规则是这产品**唯一比 B站 多的东西**(bilibili 有夹子但没有逻辑,
谁进谁出全靠手)。子 tab 是把它当附属品 —— 那和"核心资产"自相矛盾。

代价是它和夹子分了家(规则属于某个夹子,但你看这一页时看不到树)。缓解:
`/curator` 的夹子行上给一个跳转,直接跳到 `/rules` 并**定位到那个夹子的规则行**。

```
┌─ 🤖 AI 的建议  2                                     [全部采纳] ─┐
│ ┃ 「AI/编程」加一条:标题含 Agent · 大模型 · LLM                    │
│ ┃ 依据:8 条被归进别的夹子的条目,标题都含这几个词                     │
│ ┃                              [采纳] [改一下] [忽略]              │
└──────────────────────────────────────────────────────────────────┘

  夹子            规则                              命中   来源  改于
  ─────────────────────────────────────────────────────────────────
  ▾ AI/编程       标题含 Python·JS·Rust             412   🤖   2 分钟前
                   简介含 算法
  ▸ 前端          标题含 React·Vue·构建              88   ✎    昨天
  ▸ 待整理        —— 还没写规则,归类时靠 AI           —    —    —

  [＋ 新增规则]                            [⚡ 试跑:规则 vs AI]
```

界面上的四条规矩:

1. **就地展开编辑,不弹窗**。改规则时你**必须同时看着「命中几条」** —— 弹窗会把表盖住。
   加个词 → 看命中数跳 → 删掉重来,这个来回就是调规则的全部体验。
2. **AI 建议置顶且单独一栏**。它是"待你处理"的东西,不混在规则表里。
   每条可 **采纳 / 改一下 / 忽略**。
3. **「来源」列 🤖 / ✎**。一眼看出这条规则是 AI 提的还是你写的。
4. **「试跑:规则 vs AI」** —— 告诉你规则能覆盖多少条、剩下多少要给 AI。
   这是判断"规则写够了没有"的唯一依据。

**命中数在服务端一次算完**(打开面板时 + 每次改完规则后)。口径:**全库 `items`**
(不是某个夹子里的子集)—— 要回答的是"这条规则会从整个库里捞走多少条"。
3250 条 × 规则数 × 3 字段,几十毫秒量级 —— **实现时先量一下**,
慢了就退化成"只算你正在编辑的那条"。

**「试跑:规则 vs AI」的具体形态**:点一下在面板顶部加一行结果,不跳页、不弹窗 ——

```
规则覆盖 2,340 条(72%) · 剩 910 条要交给 AI · 按本地 14b 算约 8 批
```

批数用 §3 的 `batchSize` 现算。这是判断"规则写够了没有"的唯一依据,
所以它必须**顺手就能点**,而不是藏在设置里。

### 9C.5 AI 的两个通道

**(a) 归类**:见 §9C.3。低置信度的照旧填 `null` 落「未归类」。

**(b) 规则建议**。**单独一次调用**,不塞进归类那次。

理由:归类那次的输出**是一个裸 JSON 数组**,而且真机验证过小模型能吃住这个形状;
把它改成 `{assignments:[...], ruleSuggestions:[...]}` 会让输出变难,
有把已经跑通的那条路弄坏的实际风险。而建议只在"有没归上的条目"时才需要,
所以单开一次调用**只在需要时付费**,而且那次的提问更简单
("这些条目没归上,给我规则建议"),对小模型更友好。

建议的返回形状:

```jsonc
[
  {
    "folderTempId": "42",
    "field": "title",
    "any": ["Agent", "大模型", "LLM"],
    "because": "8 条被归进别的夹子的条目,标题都含这几个词 —— 看起来它们是同一类",
    // ↓ 自证:它声称这些词管用,就得说清管住哪些条目
    "evidenceItemIds": ["BV1xx", "BV1yy", "BV1zz"]
  }
]
```

**服务端必须验证每条建议**(R7,和 §9.1.1 同一思路):

| 校验 | 不过怎么办 |
|---|---|
| `folderTempId` 存在 | 丢掉这条建议 |
| `field` 是三个之一 | 丢掉 |
| `any` 非空且 ≤ 20 个词 | 截断/丢掉 |
| **`evidenceItemIds` 里的条目,用这组词**真的**能命中** | 丢掉 —— 它编的词打不中它声称的条目 |

最后那条是关键:**AI 说"这些词管用"就必须真的管用**,拿它给的条目当场跑一遍匹配就能验。
验不过的建议是幻觉,不入库。

**(c) 建议从哪来**(用户定的:两者都要):

- **跑完归类顺手给** —— 规则没覆盖住的条目聚成建议,列在规则面板顶部等你批
- **你在对话框里主动问** —— AI 分析现有规则,给出改进建议

归类是**分批**跑的(§9.3),所以建议会一批一批地来。合并规则:**按
`folderTempId + field + any 排序后的词表` 去重**,并且把各批的 `evidenceItemIds` 并起来 ——
不同批看到的是同一类条目时,合成一条更强的建议(证据更多 → 你更容易判断该不该采纳)。

**建议不落库**。跑完归类 → 随结果返回 → 面板里显示(内存);聊天里 → 内联渲染在气泡里。
采纳即落库(变成规则),忽略即消失。刷新页面会丢 —— 但它可以从"重跑一次"再得到,
而**采纳过的规则不会丢**。这是刻意的取舍:不为一个可重生的中间态加一张表。

### 9C.6 硬约束

1. 规则只能写 `work_folder_rules`。快照(`folders`)一行不碰。
2. **AI 产生的规则建议必须过 §9C.5 的验证才能入库** —— 没验过的建议不入库,连"待采纳"状态都不给。
3. 规则的 `origin` 如实记 `'ai'` / `'user'`,和 §9B.3 的 `actor` 同一个道理:**AI 的产物和你写的产物在结构上可区分,但不分等级**。
4. **锁定的夹子(默认收藏夹)不能加规则** —— 和改名/删除/移动并删除同一条规则(§9B)。
5. 一键还原(`resetWorkcopy`)连规则一起清 —— 靠 `ON DELETE CASCADE`,不写额外代码。

### 9C.7 测试

| 测什么 | 为什么 |
|---|---|
| 匹配:三个字段各命中一次;大小写不敏感;空关键词列表不命中 | 匹配算错 = 归类错,而且是静默的 |
| 一条条目命中**两个**夹子 → 两边都归(R4) | 猜错就是悄悄少一份归属 |
| 同一条件的多个条件命中 → 只算一条(不重复归) | 重复会在同一个夹子里插两次 |
| 建议验证:引用不存在的夹子 / 词打不中它给的证据条目 → **丢掉** | 防幻觉的关键一步 |
| 建议验证:`evidenceItemIds` 为空 → 丢掉(无法自证) | 不给"无法验证"的建议开口子 |
| 规则覆盖的条目**不进** AI 调用 | R5 的全部价值就在这;不测就等于没做 |
| 删夹子 / 一键还原 → 规则跟着走(CASCADE) | 孤儿规则会让命中数骗人 |
| 锁定夹子加规则被拒 | §9C.6 约束 4 |

**只手动验证**:真机上「试跑」的命中数与实际归类结果的条数是否一致。

### 9C.8 不在这一轮

- **规则的正则 / 与或非 / 权重** —— 表达力换可读性(R2)。真需要时再说
- **规则的优先级排序** —— R4 让冲突不再是错误,所以不需要优先级
- **从已有条目自动归纳规则**(AI 看一个夹子里 20 条,反推一组词)—— 有价值,但
  §9C.5 的"建议"通道已经把这件事覆盖了大半:AI 看到"这些条目没地方去"时就会提规则
- **跨会话的规则建议历史** —— 建议可重生,理由见 §9C.5

### 9C.8b 将来才会撞上的一件事:让 AI 复核规则已覆盖的条目

现在不会发生(两组不相交,R4b)。但如果哪天要做「**让 AI 看看规则归得对不对**」——
那 AI 和规则就会对**同一条条目**发表意见,那时才需要定:

- AI 能不能**加第二个归属**?(那是 R4 的自然延伸,但会让"谁定的"变模糊)
- 还是 AI 只能**建议改规则**,不能直接动归属?(保持"规则是唯一事实来源")

**倾向后者** —— 规则可执行、可复现,让它当地基;AI 的价值在于改地基,不在于绕过地基。
但这是将来的决定,本轮只在这里点名,免得靠撞上才发现。
