# §9F 标签体系(词库树 / 质检 / 规则接入)(2026-09-18)

> 新增节。前置:§3(模型接入)、§9C(规则)、§9D(可中止 AI 调用)、§9E(条目 AI 标注)。
> 与 §9E 的关系:**取代它的标签模型,保留它的 kind**。§9E 的 `items.ai_tags`(扁平字符串数组)
> 作废,改成一棵会自己生长的树;§9E 的 `kind` 受控枚举继续有效,但迁到独立列(见 C7)。

## 9F.0 为什么

§9E 上线后暴露的边界(2026-09-18,和用户的对话):标签是**自由文本**,没有类型、没有归属、
没有词表。3250 条各自生成,跨条目的"男孩 vs boy"没有人管;而用户要拿它当**规则的地基** ——

用户原话:"现在的规则部分其实没有什么根基,因为 bilibili 并没有提供 tag 信息,所以很难按照
一个标准进行有效分类…… tag 系统的建设就是基础"。

三个具体病:

1. **跨域污染**:「AI漫剧」和「AI学习」都有 AI。给 AI 漫剧的视频打了裸的「AI」,规则
   "tag 含 AI → 归到 AI 学习夹子"就错了。用户:"和 AI 漫剧有关的视频,肯定不会出现在
   AI 学习的夹子项目,因为它们就不是一种类型"
2. **重复**:同一件事被反复建成不同的词。「男孩 === boy」是用户的原话
3. **粒度**:用户要细到角色(海贼王 → 路飞)、赛事(NBA / FIBA)、菜系(粤菜 / 鲁菜)。
   扁平词表撑不住这个粒度 —— 词一多就散,散到无法用于分类

**术语澄清(对话中确认)**:用户提出的"用 deepseek flash 做二次 RAG" —— 严格说那是**级联
(cascade)**不是 RAG:RAG 有"检索外部知识"这一步,级联只是小模型不确定时升级给大模型。
区别很实际:级联只用模型自己的知识,**它不知道的永远不知道,而且会自信地编**。用户接受
这个天花板("视频的这些知识大多数情况应该都是已有模型知识"),本轮**不做检索层**。

## 9F.1 决定

| # | 决定 | 为什么 |
|---|---|---|
| C1 | 三张新表 `tags` / `tag_aliases` / `item_tags` 取代 `items.ai_tags`。**旧列不迁移、不读不写** | 现存标签是扁平词,灌进新树只是给整理环节添垃圾。新链路从零跑一轮(本地模型,全库 5 分钟级、免费)。旧列不 DROP:SQLite DROP COLUMN 有约束,而收益为零 |
| C2 | 词库是**一棵树**:节点=词,`parent_id` 为空即为根,根即"大类"。**深度 ≤ 4 层**,超出截断、截断点当根 | 用户否决"大类闭集":"大类闭集就意味着以后不会有新的大类出现了,这个不符合客观事实"。所以大类不是预先的名单,是树的分叉点;封顶防树退化成一条线(那是目录不是分类) |
| C3 | 归一化**只做确定性**的部分:trim、全角转半角、英文统一小写、去首尾标点 | 简繁和译名差异(路飞/鲁夫)字符串规则做不到,硬做只会做错。交给 C4 + C9 用语义判 |
| C4 | `tag_aliases(name → tag_id)` 是**"不重复建立"的物理保证**:被合并的旧名、大小写/简繁变体、质检问出来的答案,全部留痕;查词先查别名表 | 用户:"相同的 tag 不要重复建立,相近的 tag 也不要重复建立"。留痕一次,永久记住 |
| C5 | 标注**分两步**:① 选这条视频属于哪几个根(1-3 个)② 在每个选中根的子树下取词。输出**路径** `根/子/孙` | 这是防跨域的机制本身:FIBA 只存在于体育子树里,被判成动漫类的视频**取不到它** —— 跨域污染不是靠事后甄别挡掉的,是靠它压根不在可选项里 |
| C6 | 路径第一段必须是**已有根**(首轮允许它提新根);路径不合法整条丢弃,当没标 | 与 §9.4 归类链路的"编出来的 itemId 丢掉"同款纪律 |
| C7 | `kind` 保留为**独立的正交轴**(§9E C3 继续有效),迁到 `items.ai_kind`;**不并入树** | 形态(教学/娱乐/评测/资讯/工具)与主题(体育/动漫)是两个轴。混进树会让 C9 的晋升/合并/降级规则要给保留节点开一堆例外 —— 一列比一套例外便宜 |
| C8 | **本地模型生产,flash 质检**:质检只针对**本轮新建的词**,攒起来批量过一次 flash(新用途「标签质检」),它回答三件事:这是什么、该挂哪个根、是不是太泛**根本不该进词库**("AI""视频""教程"这类) | 用户:本地模型做生产、flash 做二次。首轮 500-1500 新词 ≈ 十几次调用,之后每轮新增几十词 ≈ 一次。**几轮后这条路趋近于零花费** |
| C9 | 整理三条规则:**合并**(同父下归一化同名 → 免费直接并;异名同义 → 语义判)/ **晋升**(某词 ≥3 个不同子词 且 覆盖 ≥20 条视频 → 提为根)/ **降级**(某根 ≤2 个子词 且 覆盖 <5 条 → 并回兄弟)。K=3 / M=20 可调 | 用户选了"涌现式:阈值自动晋升"。这是"什么算一个新大类"的**可算判据**,不是拍脑袋 |
| C10 | 每轮跑完**自动整理一次**,产出「树的变化」清单(新根 / 晋升 / 降级 / 合并)在 UI 上可见。**不需要人工审批** | 用户:"我不想管标注 tag 的事情"。所以不设审批闸 —— 但结构必须**看得见**在长什么 |
| C11 | 规则引擎加第四字段 `tag`(改 §9C R2)。匹配语义:**选中任何一个标签 = 匹配它整棵子树** | 这是"地基"落地处。选「体育」命中所有体育下的条目(标题里没写"篮球"的也能命中);选「NBA」只命中 NBA 那条线 |
| C12 | 两个页面:「标签」(治理,主视图用 antd `Tree`)+「浏览」(使用,复用现有条目列表渲染) | 用户要"表现这些 tag 以及 tag 之间的关系"和"按标签看收藏",且明确要两个页面。主视图用树不用图:树能显示每个节点覆盖多少条、能右键操作,图不能 |
| C13 | 「授权」页加第五个用途 `tagcheck`(「标签质检」);传输/中止/进度/逐批落库**照抄 §9D 与 tagRoutes**,不发明新东西 | §9D 的 SSE + progress + stop 已经跑通,重写一遍是纯浪费 |

### 新大类是怎么诞生的(用户最关心的一条)

首轮之后,模型**只能挂在已有根下** —— 那新领域怎么办?靠 C9 的晋升,两步走:

```
第 N 轮  露营的视频来了 → 模型挂在「生活」下(没有别的根可挂)
         ↓ 越来越多露营的词:帐篷、天幕、营地、野炊、露营装备…
第 N+M 轮 「露营」下面挂了 8 个不同的子词、覆盖 47 条视频
         → 满足 K=3 / M=20 → 自动升为根
```

所以"新大类出现时还是要新建一个类别准确储存"这件事成立,**而且不需要谁来批准** ——
判据是算出来的(子词数 + 覆盖条目数),不是名单里有没有。反过来,一个大类长期长不出东西
(≤2 个子词、<5 条),它本来就不是大类,降级并回去。

## 9F.2 数据模型

```sql
tags(
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,                      -- 规范名(显示用)
  parent_id INTEGER REFERENCES tags(id),   -- NULL = 根
  created_at INTEGER
)
UNIQUE(parent_id, name)                    -- 同一父下不许重名:第一层防重复

tag_aliases(
  name TEXT PRIMARY KEY,                   -- 所有见过的写法(原始形态)
  tag_id INTEGER REFERENCES tags(id)
)

item_tags(
  item_id TEXT REFERENCES items(id),
  tag_id INTEGER REFERENCES tags(id),
  source TEXT,                             -- 'ai' | 'rule' | 'user'
  PRIMARY KEY(item_id, tag_id)
)

-- items 变动:新增 ai_kind TEXT(C7);ai_checked_at 复用为增量水位线;
--             ai_tags / ai_summary 标为废弃(不读不写,不 DROP)
```

**合并为什么必须换表**:合并 A→B 时,把所有挂 A 的视频改挂 B。因为视频挂的是**关联**而不是
字符串,所以"合并是改词,所有视频自动跟着走"—— 这是从 `ai_tags` 一列换成三张表的唯一理由。

## 9F.3 运行方式

```
点「AI 标注」(规则页,入口不变)→
  ① 读 readLlmSettings('tag')      本地小模型
  ② 取 ai_checked_at IS NULL 的条目(增量);「重新标注全部」则全量
  ③ 两步标注:先选根(1-3)→ 再在子树下取词 → 路径 根/子/孙(≤4 层)
     → 落库(0 token):别名表 → 树 → 新建节点 → 写 item_tags
     → 逐批落库(§9D A3 既有模式),可中止(§9D B2 全套)
  ④ 跑完自动整理:
     · 质检:本轮新建的词 → 批量问 flash(「标签质检」)→ 补别名、纠正父节点、剔除过泛词
     · 合并 → 晋升(K) → 降级(M)
     · 产出「树的变化」清单 → 回给 UI
```

**一条视频的模型输出形状**(示意):

```json
{"id":"BV1xx","kind":"娱乐","tags":["动漫/海贼王/路飞","动漫/热血"]}
```

`kind` 与 `tags` 同一次调用产出(C7 它是正交轴,但没必要为它多跑一趟)。

**子树匹配的实现**(C11):预计算每个节点的祖先闭包,3250 条全内存,一次查询建
`Map<itemId, tagIds[]>`。不递归查库。

## 9F.4 与既有条款的关系

- **§9E C1 被取代**:`ai_tags` 那列退休;C3(kind 受控枚举)、C4(逐条覆盖断言)、
  C7(增量/全量)、C8(入口在规则页)全部保留
- **§9E C5 保留并升级**:`renderItem` 仍加标签行,但渲染的是树标签(叶名),归类因此看得更清
- **§9C R2 破一次**:规则的字段从三个变四个(C11)。这是 §9E.5 明确押后的事项,现在标签
  质量由 C8/C9 保证,条件成熟
- **§3 加第五个用途**(C13)。改动是手写的三处:服务端 `LlmPurpose` / 前端同名联合类型 /
  两个 `PURPOSE_LABELS` 与写死的"四个用途"文案
- **§9E.5 的「B站官方标签同步」明确继续不做**:用户否决 —— "不用考虑 3250 次请求,
  这个太慢,而且容易被风控,我们自己建立就可以"

## 9F.5 明确接受的天花板

- **质检仍会漏**:flash 说不清的词(冷门新番角色、极小众术语)只能留在树里。它不会因此
  被删掉,只是可能挂错父节点 —— 下一轮合并/晋升会再收拾
- **晋升阈值是启发式**(K=3/M=20),不是真理。它决定"根多根少":K 小则象限细,K 大则
  都往大领域里塞。这是旋钮不是正确答案,页面上可调
- **重跑会改变树的形状**:合并不可逆(旧名进别名表,节点删掉)。树的每一次变化都在清单里
  可见,但**没有"撤销上一轮整理"**
- **确定性归一化不做简繁/译名**,这些只在合并环节靠语义判 —— 判错就是判错,没有第二道闸
