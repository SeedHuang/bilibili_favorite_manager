# §9F 标签体系(词库树 / 质检 / 规则接入)(2026-09-18)

> 新增节。前置:§3(模型接入)、§9C(规则)、§9D(可中止 AI 调用)、§9E(条目 AI 标注)。
> 与 §9E 的关系:**取代它的标签模型,保留它的 kind**。§9E 的 `items.ai_tags`(扁平字符串数组)
> 作废,改成一棵会自己生长的树;§9E 的 `kind` 受控枚举继续有效,但迁到独立列(见 C7)。

## 9F.0 为什么

§9E 上线后暴露的边界(2026-09-18,和用户的对话):标签是**自由文本**,没有类型、没有归属、
没有词表。3250 条各自生成,跨条目的"男孩 vs boy"没有人管;而用户要拿它当**规则的地基** ——

用户原话:"现在的规则部分其实没有什么根基,因为 bilibili 并没有提供 tag 信息,所以很难按照
一个标准进行有效分类…… tag 系统的建设就是基础"。

三个具体病:

1. **跨域污染**:「AI漫剧」和「AI学习」都有 AI。给 AI 漫剧的视频打了裸的「AI」,规则
   "tag 含 AI → 归到 AI 学习夹子"就错了。用户:"和 AI 漫剧有关的视频,肯定不会出现在
   AI 学习的夹子项目,因为它们就不是一种类型"
2. **重复**:同一件事被反复建成不同的词。「男孩 === boy」是用户的原话
3. **粒度**:用户要细到角色(海贼王 → 路飞)、赛事(NBA / FIBA)、菜系(粤菜 / 鲁菜)。
   扁平词表撑不住这个粒度 —— 词一多就散,散到无法用于分类

**两条术语澄清(对话中确认)**:

- 用户提出的"用 deepseek flash 做二次 RAG" —— 严格说那是**级联(cascade)**不是 RAG:
  RAG 有"检索外部知识"这一步,级联只是小模型不确定时升级给大模型。区别很实际:级联只用
  模型自己的知识,**它不知道的永远不知道,而且会自信地编**。用户接受这个天花板
  ("视频的这些知识大多数情况应该都是已有模型知识"),本轮**不做检索层**
- 判"什么算一个新大类"时,用户拒绝了"靠拍的阈值":"我拍的肯定不行,你要有判断依据吧,
  你让 flash 来拍,flash 也要有一定的依据吧,不然都是乱拍"。**这一条决定了 C9** ——
  判据必须是**可算的证据**,而不是任何一方给的数字

## 9F.1 决定

| # | 决定 | 为什么 |
|---|---|---|
| C1 | 三张新表 `tags` / `tag_aliases` / `item_tags` 取代 `items.ai_tags`。**旧列不迁移、不读不写** | 现存标签是扁平词,灌进新树只是给整理环节添垃圾。新链路从零跑一轮(本地模型,全库 5 分钟级、免费)。旧列不 DROP:SQLite DROP COLUMN 有约束,而收益为零 |
| C2 | 词库是**一棵树**:节点=词,`parent_id` 为空即为根,根即"大类"。**深度 ≤ 4 层**,超出截断 | 用户否决"大类闭集":"大类闭集就意味着以后不会有新的大类出现了,这个不符合客观事实"。所以大类不是预先的名单,是树的分叉点;封顶防树退化成一条线(那是目录不是分类) |
| C3 | 归一化**只做确定性**的部分:trim、全角转半角、英文统一小写、去首尾标点 | 简繁和译名差异(路飞/鲁夫)字符串规则做不到,硬做只会做错。交给 C9 的集合判据 |
| C4 | **一个名字在整棵树里只对应一个节点**(全局唯一)。`tags.norm` 是那个全局键(`UNIQUE(norm)`),`tag_aliases(name → tag_id)` 装的是**不再是任何节点规范名的写法**:被合并掉的旧名、改名前的旧名、简繁/大小写变体。查词 = 先查 `tags.norm`,再查别名表 | 用户:"相同的 tag 不要重复建立,相近的 tag 也不要重复建立"。**全局唯一才是那句话的字面意思** —— 允许"不同父下同名"会造出两个 `篮球`、两个 `露营`,而那正是他要避免的重复。(这一版初稿写过"作用域唯一",它引出一串连锁:改名把子节点旧名写进全局别名表造出假根、提升子节点撞唯一索引、质检按名字寻址在同名节点里任意命中一个 —— 而最要命的是"同一个词挂到两个领域下会短暂存在两个节点、由 C9 合并掉"**是假的**:那两批视频几乎不相交,覆盖率双向为 0,永远不合并,于是永久并存且界面上看不出来) |
| C5 | 标注**两步,但第一步不受约束**:① 说出这条视频属于哪些领域(1-3 个,可以是新的)② 取词,词挂在**第一个**领域下 | 第一步是给模型的思考台阶(先想"这是什么世界"再选词),**不是准入闸**。早先写成"只能从已有根里选"是错的(见下方"新大类怎么诞生")——那时树还不存在,逼它选等于逼它瞎猜。**输出不是完整路径**:让 4b 吐 `领域/子/孙` 三段它会错,而"词挂第一个领域"一句话就够 —— 更深的关系由质检的 move(C8)和判据的 reparent(C9)从数据里长出来 |
| C6 | 校验只做结构性检查:itemId 在本批内、名字非空。不合法的整条丢弃,当没标。**树深封顶 4 层** —— 闸门放在**唯一收口** `setTagParent` 里(挂父/挂到自己后代/超深都返回 false 而不是抛),`mergeTags` 另查一次(它换的是整棵子树) | 与 §9.4 归类链路的"编出来的 itemId 丢掉"同款纪律。**不做"第一段必须是已有根"的校验** —— 那是 C5 旧版的漏洞来源。封顶防树退化成一条线(那是目录不是分类)。**闸放收口不放在各调用点**:质检的 move、判据的 reparent、手动 PATCH、手动合并共四条路,分散着写必然漏 —— 而且**挂到自己后代**会造出环,环上的节点全都不是 root,整段子树会从页面上消失 |
| C7 | `kind` 保留为**独立的正交轴**(§9E C3 继续有效),迁到 `items.ai_kind`;**不并入树** | 形态(教学/娱乐/评测/资讯/工具)与主题(体育/动漫)是两个轴。混进树会让 C9 要给保留节点开一堆例外 —— 一列比一套例外便宜 |
| C8 | **本地模型生产,flash 质检**。质检做三件事:① 剔除**裸泛词**("AI""视频""教程"这类,根本不该进词库)② 定每个新词在树里的位置(是根,还是挂到某词下)③ 首轮把全部新词**组织成一棵树** | 用户:本地模型做生产、flash 做二次。**首轮所有词都是新的、且没有任何数据**,那时唯一的依据就是先验知识 —— 这是 flash 该出场的地方。之后每轮只剩几十个新词,≈ 一次调用 |
| C9 | **判据是集合关系,不是任何阈值**:看两个词挂的是不是同一批视频。`覆盖(A→B) = \|A∩B\| / \|A\|`。**A 是 B 的子**(覆盖 ≥90%)/ **A ≡ B 合并**(双向都 ≥90%)/ **平级**(覆盖都低)。样本 <5 条不判,保留 C8 的先验 | 用户:"你要有判断依据吧"。这就是依据 —— 一个词在你收藏里的真实含义,写在"它挂了哪些视频"里。**降级/晋升这类靠拍的阈值(K=3/M=20)整套删除**(理由见下) |
| C10 | 每轮跑完**自动整理一次**,产出「树的变化」清单(新根 / 合并 / 挂父变化)在 UI 上可见。**不需要人工审批** | 用户:"我不想管标注 tag 的事情"。所以不设审批闸 —— 但结构必须**看得见**在长什么 |

| C12 | 两个页面:「标签」(治理,**手写树**,照 `WorkFolderTree.tsx` 的模式)+「浏览」(使用,复用现有 `ItemGrid`/`ContextPane` 渲染) | 用户要"表现这些 tag 以及 tag 之间的关系"和"按标签看收藏",且明确要两个页面。主视图用树不用图:树能显示每个节点覆盖多少条、能操作,图不能。**不用 antd `Tree`** —— 仓库里它零使用,现有树形 UI(夹子/条目)全是手写的(自管展开态、勾选、inline 改名),样式也自成一套 |

### 判据:为什么是集合关系,不是数数

用户原话:"露营没有这个大类,但是美食有,所以就关在美食下面了是吧" —— **那是错的**,而且是
旧设计的真实漏洞:把"该挂哪"压给了"树里已经有什么",可新领域第一次出现时树上什么都没有。

改法是把这一步交给**证据**,而证据就是你自己的收藏:

| 关系 | 判据 | 结论 | 例(数字为示意) |
|---|---|---|---|
| A 挂的几乎**全在** B 里 | 覆盖(A→B) ≥ 90% | **A 是 B 的子** | 烤羊肉 15 条,全在美食 300 条里 → 挂美食下 |
| A 和 B **几乎重合** | 双向覆盖都 ≥ 90% | **两者是同一个东西 → 合并** | 路飞 30 / 鲁夫 28,重合 28 → 合并 |
| A 和 B **各挂各的** | 覆盖都低 | **平级** | 露营 47 / 美食 300,重合 12 → 两个根 ✅ |

第三行就是"烤羊肉"那个例子的**自动纠正**:露营和美食各挂各的,谁也盖不住谁,平级。

**所以整套阈值(K=3 / M=20)被删除**,连同它带来的"晋升 / 降级"两个动作。理由:

- 那两个数**没有任何依据**,是拍出来的。用户一句"我拍的肯定不行"就否掉了
- 更糟的是它们**和质检打架**:质检判"露营是根",计数判"它只有 3 条视频、降级"——
  一个建一个拆,结构会来回晃。而**降级是破坏性的**:拆掉一棵正确的树比不拆糟得多
- 现在没有任何事需要计数来判了:该不该是根由 C9 的覆盖关系说,建错了由下一轮的数据改判

**唯一剩下的两个数**(性质与原来的不同,都是可解释判据的临界值):
覆盖面 ≥90%(调高→层级更浅、更多平级;调低→更多嵌套)和统计下限 5 条(少于它,重合率
没有统计意义 —— "两个词各挂 1 条、恰好是同一条"说明不了任何事)。

### 新大类是怎么诞生的(这条替代原来的"晋升规则")

```
首轮   没有树可参考 → C8 的质检把全部新词组织成初始树(纯先验)
       ↓
第 N 轮 露营的视频来了:模型把它当普通词说,挂在「生活」下 —— 它这时是**子节点**
       ↓ 越来越多露营的词:帐篷、天幕、营地、野炊、露营装备…
第 N+M 轮 模型开始把「露营」放进 domains 里(它确实已经是一个领域了)
       → 落库时**把它从「生活」下提出来、变成根**(C5 的落库规则)
       ↓
第 N+M 轮 数据也长起来了 —— 露营 47 条、美食 300 条、重合 12 条
       → C9 算出:谁也盖不住谁 → 两个根平级 ✅
```

**"提成根"那一步是必要的,不是可选的。** 全局唯一(C4)让 `ensureTag` 复用已有节点,
所以一个词**一旦当过子节点就永远是** —— 判据只挪根、质检的 move 也只能挪到别的词底下。
不提的话这条路是死的,而模型把它放进 `domains` 是它唯一的信号源。

**为什么 C9 只挪根**:已经有父的节点是**质检给的判断**;数据只纠正"没有父"的那些。
所以一个词想被数据重新安置,前提是它得先是根 —— 这也是"提出来"必须在落库时就做的原因。

反过来也成立:提错了不要紧 —— 下一轮判据发现它的视频全落在某个词里,会把它挂回去。

## 9F.2 数据模型

```sql
tags(
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,                      -- 显示名(首次见到的写法)
  norm TEXT NOT NULL UNIQUE,               -- 归一化后的**全局身份**(小写/半角/去首尾标点)
  parent_id INTEGER REFERENCES tags(id),   -- NULL = 根
  created_at INTEGER
)
-- norm 全局唯一(C4)—— 一个名字全树只有一处。
-- 不需要 (parent_id, norm) 那层:父不参与唯一性。

tag_aliases(
  name TEXT PRIMARY KEY,                   -- 归一化后的写法
  tag_id INTEGER REFERENCES tags(id)       -- 它现在归哪个节点
)
-- 装的是**不再是任何节点规范名**的写法:合并掉的旧名、改名前的旧名、简繁变体。
-- 它和 tags.norm 一起构成"查词"的全部依据:先查 norm,再查这张表。

item_tags(
  item_id TEXT REFERENCES items(id),
  tag_id INTEGER REFERENCES tags(id),
  source TEXT,                             -- 'ai' | 'rule' | 'user'
  PRIMARY KEY(item_id, tag_id)
)

-- items 变动:新增 ai_kind TEXT(C7);ai_checked_at 复用为增量水位线;
--             ai_tags / ai_summary 标为废弃(不读不写,不 DROP)
```

**合并为什么必须换表**:合并 A→B 时,把所有挂 A 的视频改挂 B。因为视频挂的是**关联**而不是
字符串,所以"合并是改词,所有视频自动跟着走"—— 这是从 `ai_tags` 一列换成三张表的唯一理由。

**C9 怎么算**:词 → 它挂的视频 `Set`,**一次算完全部有向覆盖率**存进一张表
(`"a,b" → |A∩B|/|A|`,零交集的不存),后面判据查表而不是现算。
`ponytail: 几千个词时全量对是 O(n²) 次求交,秒级;上万词再考虑倒排表预筛或 minhash。`
(初稿写的是"只算同现过的候选对",实现并没有做那层预筛 —— 别照那句去核代码。)

## 9F.3 运行方式

```
点「AI 标注」(「标签」页 —— 入口从规则页改址,理由见 §9F.5)→
  ① 读 readLlmSettings('tag')      本地小模型
  ② 取 ai_checked_at IS NULL 的条目(增量);「重新标注全部」则全量
  ③ 两步标注:说领域(可新)→ 在领域下取词 → 路径(≤4 层)
     → 落库(0 token):别名表 → 树 → 新建节点 → 写 item_tags
     → 逐批落库(§9D A3 既有模式),可中止(§9D B2 全套)
  ④ 跑完自动整理:
     · 质检(flash):剔除裸泛词 → 定新词在树里的位置(首轮 = 组织整棵树)
     · 集合判据(0 token):合并 / 挂父纠正
     · 产出「树的变化」清单 → 回给 UI
  ⑤ 你点「提体系」时(C15)—— 它的输入已经换成
     「夹子名 + 夹子画像 + 规则 + 样本」→ 模型提现有夹子的改进
     (该合并 / 该拆 / 规则该改)。是建议,点了才应用

     **这一步不自动跑**:Pass 1 的产物是**会话级草稿**(可能是你正在编辑的那份),
     自动触发会盖掉你的东西。C15 要的是"依据变好了",不是"自动帮你改"
```

**thinking 必须能按环节关**(待补项)。`deepseek-flash` **默认走思考模式**,而这条路里
批量环节(标注、归类、质检)要的是"照格式吐 JSON",不是"想清楚" —— 每批吐一长串推理,
输出 token 涨数倍、整体变慢。`llm/provider.ts` 现在只把 reasoning 透传出来给前端看,
**没有开关**。细节与费用影响见 §3 末那节。

**一条视频的模型输出形状**(示意):

```json
{"id":"BV1xx","kind":"娱乐","domains":["美食","户外"],"tags":["露营","烤羊肉","新疆"]}
```

`kind` 与 `tags` 同一次调用产出(C7 它是正交轴,但没必要为它多跑一趟)。`domains` **不受
已有树的约束** —— 它是模型的思考台阶,不是准入闸(C5)。

**子树匹配的实现**(C11):预计算每个节点的祖先闭包,3250 条全内存,一次查询建
`Map<itemId, tagIds[]>`。不递归查库。

**夹子画像**(C14):每个**工作夹子**内视频的标签频次一次查询算出来,内存统计。离群判定
零参数 —— 一条视频若它每一个标签在该夹子其他视频身上都不出现,就是离群(夹子条目 <5 不判,
与 C9 同一个统计下限)。

## 9F.4 模型分工与费用

**分界线:模型只做代码替代不了的事 —— 理解一个没见过的词、看一条标题说它讲什么。
凡是"算关系"的活,全归代码。**

### 用模型的

| 场景 | 用途 | 模型 | 干什么 | 量 |
|---|---|---|---|---|
| 条目标注 | `tag` | 本地 `qwen3-4b` | 看标题+简介 → 领域、标签、kind | 250-400 次/全库 |
| 标签质检 | `tagcheck`(C13 新增) | flash | 判词:剔泛词 / 定位置 / 首轮组织整棵树 | 首轮 10-30 次,之后 1 次/轮 |
| 提体系 + 夹子改进 | `classify` | flash | 拿 画像 + 规则 看现有夹子(C15) | 1 次/轮 |
| 归类 Pass 2 | `classify` | flash | 逐批产出归属 | 1 次/轮 |
| 规则建议 | `rules` | flash | 未归条目 → 规则建议 | 1-3 次 |
| 管家聊天 | `chat` | flash | 流式答复 | 你驱动 |

### 不用模型的(0 token)

集合判据(C9)、夹子画像与离群标记(C14)、规则匹配、子树匹配(C11)、别名查询与归一化(C3/C4)。

### 为什么用途是 5 个、不拆

一度想给「提体系」单开一个槽(`taxonomy`),理由是它要最强的模型、而归类要性价比。
**查到数据之后撤回了**,两层原因:

1. **前提不成立**:flash 本身就是第一梯队。LiveBench 2026-06-25 表(官网可下载的最新一版)
   里 `deepseek-v4.1-flash-max` **81.11 分,58 个模型排第 5** —— 榜首 83.41
   (`claude-fable-5-1-max-effort`),中位数 75.54,而它**比 `claude-opus-5-max-effort`(80.08)
   还高**。所以"提体系用旗舰、归类用便宜"**没有第二个模型可用**,一个槽同时满足两边
2. **钱不对**:我最初用"33 倍"论证要拆,那是 **token 量**之比(归类一轮约 100 万、
   提体系约 3 万)。换成钱按官方价(off-peak)算:归类整轮约 **$0.5**,提体系一次
   **不到一分钱**。几毛钱的差别不值得多一个下拉

**用途维持 5 个**:`chat` / `classify` / `rules` / `tag` / `tagcheck`。要拆随时是改一个
下拉加一行文案的事 —— 但先拆再合是白拆。

### 费用(3250 条全库,off-peak)

价格 per 1M token:输入 cache-hit $0.003 / cache-miss $0.15;输出 $0.60。
peak = UTC 01:00–04:00 与 06:00–10:00 周一至周五 = **北京时间工作日 09:00–12:00、
14:00–18:00**(其余时间全半价 —— **晚上跑省一半**)。

| 环节 | 输入 | 输出 | 费用 |
|---|---|---|---|
| 打标(本地) | — | — | **$0** |
| 标签质检 | 首轮 ~60K / 之后 ~3K | ~30K / ~2K | 首轮 **~$0.03** / 之后 $0.002 |
| 提体系 + 夹子改进 | ~30K | 10–30K | **~$0.02** |
| 归类 | 850K(81 万 miss + 4 万 hit) | 195K | **~$0.24** |
| 规则建议 | ~5K | ~2K | ~$0.005 |

**首轮全库 ≈ $0.3(约 ¥2);之后每轮增量 ≈ $0.01–0.03。**
**这次改动新增的部分** = 打标 $0 + 质检 $0.03 + 提体系 $0.02 = **首轮五分钱、之后每轮两厘**
(归类本来就在花钱,不是这次加的)。

**五个费用杠杆**,按影响排序:

1. **thinking 开关** —— 唯一的显著项。上表归类那 195K 输出是**关 thinking**算的;
   开满推理输出涨 2-3 倍,一轮从 $0.24 涨到 **$0.5–0.75**
2. **off-peak** —— 直接减半。别在工作日白天跑全量
3. **cache hit 比 cache miss 便宜 50 倍**($0.003 vs $0.15)。每批重复发的 system prompt
   与夹子规格全走 cache hit,上表已按此算
4. **打标走本地只省 $0.22/轮** —— 不多。选本地小模型真正的理由是 **3250 条标题不出本机、
   不排队**,不是省钱
5. **换 `deepseek-v4-pro` 是 3.8 倍**:同一轮 ~$0.92 vs $0.24。**也还不到一块钱**

**结论:费用在这个规模上不构成决策依据。** $0.3 与 $0.9 的差别不该左右"拆不拆用途"这类
架构选择 —— 真正的成本是人的时间。

> 数据来源:[livebench.ai](https://livebench.ai/)(`table_2026_06_25.csv`)、
> [DeepSeek API 文档 · 模型 & 价格](https://api-docs.deepseek.com/quick_start/pricing)。
> **LiveBench 是英文基准,没有中文、也没有"把中文词归类到领域"这种任务** —— 它是代理指标,
> 不是本任务的测量。真要定论,拿首轮的新词跑一次对照:`tagcheck` 分别指 flash 和旗舰各跑一遍,
> 看分歧率。

## 9F.5 与既有条款的关系

- **§9E C1 被取代**:`ai_tags` 那列退休;C3(kind 受控枚举)、C4(逐条覆盖断言)、
  C7(增量/全量)全部保留
- **§9E C8 的入口改址**:「AI 标注」从「规则」页搬到「标签」页。§9E 当时的理由
  ("标注存在的理由就是让归类更准,和规则/试跑放一起")在 §9F 之前是成立的 ——
  但 **§9F 改掉了那个前提**:这一跑会**长出词库树**(C5),而树有自己的页面。
  让"产出这一页全部内容的动作"要求用户去别处按,说不通。C8 的其余部分
  (进度走 §9D 的 progress 帧模式)不变
- **§9E C5 保留并升级**:`renderItem` 仍加标签行,渲染树标签(叶名)**加 kind** ——
  两样都得渲染。只渲染标签的话,C7 那个"独立正交轴"会变成一个**只写不读的死列**:
  占一列、占标注的输出 token、进不了 prompt、界面上也不显示。kind 要继续有用,
  就必须继续出现在模型眼前(它是 §9E 实测唯一被验证过有用的那个信号)
- **§9C R2 破一次**:规则的字段从三个变四个(C11)。这是 §9E.5 明确押后的事项,现在标签
  质量由 C8/C9 保证,条件成熟
- **§3 加第五个用途**(C13)。改动是手写的三处:服务端 `LlmPurpose` / 前端同名联合类型 /
  两个 `PURPOSE_LABELS` 与写死的"四个用途"文案
- **§9E.5 的「B站官方标签同步」明确继续不做**:用户否决 —— "不用考虑 3250 次请求,
  这个太慢,而且容易被风控,我们自己建立就可以"
- **§3 的模型注册表清了一次**(2026-09-18,顺带做):删掉已退役的 `deepseek-v4-flash` /
  `deepseek-chat` / `deepseek-reasoner`,补上**漏记的** `deepseek-flash`,并钉上一条规矩
  —— 「这张表只收厂商现在在售的模型」(它是「模型管理」下拉的数据源,留退役名 = 让用户
  能选到用不了的东西)。同时记下 **thinking 开关是待补项**(§3 末)
- **两代 flash 同名,别搞混**:`deepseek-v4-flash`(V4,已退役)在 LiveBench 上是 65.48,
  `deepseek-v4.1-flash-max`(V4.1)是 81.11 —— **差 15.6 分**。我们表里的 `deepseek-flash`
  是后者(9F.4 的选型结论建立在后者之上)

## 9F.6 明确接受的天花板

- **集合判据对付不了泛词,而且会把它推到树顶**:一个挂遍全库的词,覆盖关系上"所有词都
  在它里面" → 判成根。所以**剔除裸泛词必须留在质检**(C8 ①),这是这套判据唯一的软肋
- **判据建立在"标签挂得大致对"之上**:标注错得离谱时集合关系跟着一起错。它校验的是词与
  词的关系,**不校验词与视频的关系**
- **首轮纯靠先验**:数据一条没有,C9 完全失效,树长什么样全看 flash。第一轮之后的每一轮
  都在纠正它,但**第一轮的形状会留在用户看到的界面上**
- **重跑会改变树的形状**:合并不可逆(旧名进别名表,节点删掉)。树的每一次变化都在清单里
  可见,但**没有"撤销上一轮整理"**
- **夹子画像会跟着夹子里的脏数据走**:一个夹子如果本来就一半放错了,它的"画像"就是错的,
  离群标记也就跟着不准。它照的是镜子,不是裁判
- **"提体系"提错了不致命**:它是**建议,点了才应用**,代价是"再跑一次 + 看一眼",不是
  不可逆的破坏 —— 真正不可逆的只有写回 B站那一步(M5)。这条推翻了本文档早先的说法
  (我曾写"提体系错了代价最大、没法自愈",那是说过头了,基于"你会照着它归 3250 条"的
  假设;实际上归类结果同样要你点 `/apply` 才生效)
- **现有夹子的改进质量,天花板是标签质量**:C15 让模型拿标签和规则当依据去提改进 ——
  标签树错了,依据就是错的。这是个正反馈环,好方向和坏方向都会自增强

## 9F.7 不在这一轮

- **力导向图视图**(Obsidian 那种知识图谱)—— 主视图用手写树(零新依赖)已经够治理;
  图适合"看形状、发现孤岛",不适合"查 NBA 底下有几条"。前端现在没有任何图形库,要装
  d3-force 或手写 SVG,是个独立决定
- **embedding 向量** —— C9 的集合判据已经把"同义合并"的活干了(挂的是同一批视频 ⇒
  是同一个东西),比向量相似度更硬。真要语义近似的场景(一个词只挂 1-2 条视频时)再说
- **B站官方 tags / 分区同步**(§9E.5 原文,用户明确否决)
- **`ai_summary`** —— 建表时预留的列,至今无人写,继续闲置
